# 第 01 章 · 布局心智模型：盒模型、格式化上下文与层叠

> 这一章**不教你任何一个"布局技巧"**，但它是后面 Flexbox、Grid 全部内容的地基。
>
> 读完它，你会理解三件事：为什么 `width: 300px` 有时渲染成 342px、为什么 `overflow: hidden` 能"莫名其妙"解决高度塌陷、为什么 `z-index: 9999` 有时候按不住一个 `z-index: 1` 的元素。
>
> 本章你需要记住的就一件事：**CSS 布局不是"属性堆叠"，而是"浏览器在几套看不见的规则层里替你算"。** 盒模型决定元素占多大，格式化上下文决定元素之间怎么互相影响，层叠上下文决定谁盖住谁。这三套规则你看不见，但每一套都精确决定着你页面上每一个像素的归属。

---

## 1.1 盒模型：`width` 到底量的是哪一段

先说结论：**`width` 从来不是"这个元素占多大"，而是"这个元素的内容区占多大"——除非你把 `box-sizing` 改成 `border-box`。**

这是新手最常踩的第一颗雷，而且它隐蔽在"看起来没报错"里。写一段代码你感受一下：

```html
<div class="card">
  我设了 width: 300px
</div>
```

```css
.card {
  width: 300px;
  padding: 20px;
  border: 1px solid #000;
  background: #fdecec;
}
```

你在开发者工具里量一下这个 `.card` 的实际宽度，会发现它不是 300px，而是 **342px**。

为什么？因为默认的 `box-sizing: content-box` 把 `width` 定义为**纯内容区**的宽度，`padding` 和 `border` 是在这个 300px 的**外面**再往上加的：

```text
实际占用宽度 = width(300) + padding-left(20) + padding-right(20) + border-left(1) + border-right(1)
             = 342px
```

这就是 **content-box** 模型：`width` 只量内容，边距、边框全在外面另算。

### 先看清盒子的四层结构

理解盒模型，先记住一个盒子从里到外的四层：

```text
margin  ┊ 外边距（最外层，不参与"宽高"，只决定和别人的间距）
border  ┊ 边框
padding ┊ 内边距（背景会延伸到这里）
content ┊ 内容区（width/height 量的是这一层，在 content-box 下）
```

其中 `margin` 永远在盒子"尺寸"之外，`box-sizing` 怎么改它都不参与宽高计算。真正有歧义的是 `width` 到底包不包含 `padding` 和 `border`——这就是 content-box 和 border-box 的唯一区别。

### content-box 的问题：百分比布局会直接翻车

单看一个盒子，342px 无非是"比我预期宽一点"。但一旦进入百分比布局，content-box 的坑就从"丑"升级成"坏"：

```html
<div class="row">
  <div class="col">左</div>
  <div class="col">右</div>
</div>
```

```css
.row {
  width: 600px;
  border: 1px solid #000;
}

.col {
  float: left;
  width: 50%;        /* 两个 50%，加起来正好 100%，看起来没毛病 */
  padding: 0 20px;   /* ❌ 每个 col 的实际宽度变成 50% + 40px */
  box-sizing: content-box;
  background: #fdecec;
}
```

你心里算的是"两个 `50%` 正好把一行占满"。但浏览器算的是：每个 `.col` 占 `300px + 40px = 340px`，两个加起来 **680px**，超出一行，于是第二个 `.col` 被挤到下一行去了。

**这就是 content-box 的致命问题**：它要求你永远"心里换算"——`width` 是内容宽，实际占位还要加 padding 和 border。一旦用百分比、一旦改 padding，这个换算就得重做。

### border-box：让 `width` 变成"我占多大就设多大"

`box-sizing: border-box` 改变的是这个定义：

```text
box-sizing: border-box
实际占用宽度 = width（固定）
内容区宽度 = width - padding - border（浏览器替你减）
```

还是上面那段，改成 `border-box`：

```css
.col {
  float: left;
  width: 50%;
  padding: 0 20px;
  box-sizing: border-box;   /* ✅ */
  background: #fdecec;
}
```

现在两个 `.col` 各占精确的 `50% = 300px`，padding 从这 300px 里面扣，内容区自动变成 `300 - 40 = 260px`。一行正好塞下，不换行。

**`border-box` 的意义是：把"外扩"变成"内缩"。** `width` 从"内容的宽度"变成了"整个盒子的宽度"，padding 和 border 不再往外撑，而是往里挤内容。

### 为什么 `border-box` 是标配

三个理由：

1. **符合直觉**。你在设计稿上量一个卡片是 300px 宽，写 `width: 300px` 就该是 300px。content-box 逼你额外心算"300 + 两边 padding"，border-box 不需要。
2. **百分比不翻车**。`50% + 50% = 100%` 这个等式只有在 border-box 下才成立，content-box 下加任何 padding 都会破。
3. **改 padding 不用改 width**。border-box 下你想给按钮加点内边距，直接加，按钮总宽不变；content-box 下加 padding 等于把按钮整体撑大，你得同时缩小 width 去抵消。

### 为什么没有一个 `margin-box`？

你可能会问：既然 border-box 这么好，为什么不再进一步，让 `width` 连 margin 也包含进去？

**因为 margin 的语义是"间距"，不是"尺寸"。** 盒子本身多大，和盒子离别人多远，是两件事。margin 还承担着一个关键能力——**负值**（`margin-left: -20px` 能把元素往左拉出边界），以及 `margin: auto` 的"自动分配剩余空间"（这正是水平居中的原理）。如果把 margin 也卷进 width 里，这些能力全都会变味。

所以规范把边界画在 border：**border 以内是"盒子自己有多大"，border 以外（margin）是"盒子跟别人隔多远"。** 这条边界，就是 border-box 名字的由来。

### 全局 `box-sizing` 的由来

既然 `border-box` 是直觉，为什么浏览器默认还是 `content-box`？

**历史包袱。** CSS2 时代定下 `content-box` 为默认值时，还没有"响应式布局""百分比栅格"这些需求，网页大多是固定像素宽度，撑一点就撑一点。等后来需求变了，默认值却已经不能改了——改了会让全世界的旧页面瞬间崩掉（CSS 为了向前兼容，几乎从不改默认值）。

所以前端社区约定俗成，在每份样式表最顶部写这一行，把默认值"拨回来"：

```css
/* 全局强制 border-box：所有元素，包括伪元素 */
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

三个要点：

1. **`*` 覆盖所有元素**，让 `div`、`p`、`input` 全都统一成 border-box。
2. **`*::before` 和 `*::after` 必须单独列**——`*` 不匹配伪元素，而伪元素常常被用来画装饰（比如前面 clearfix 的 `content: ""`），它们默认也是 content-box，不一起拨会漏。
3. **放在最顶部**，让后续所有规则都在"border-box"这个心智下写，不用再惦记默认值。

一个容易被忽略的细节：**表单元素（`input`、`textarea`、`select`）的默认 `box-sizing` 和普通 `div` 并不总是一致**，浏览器对表单控件有一套自己的样式（这就是为什么原生 `input` 看起来和你设的宽高对不上）。全局那三行 `*` 选择器会把它们也统一拨到 border-box，这也是为什么你几乎看不到有人只给 `div` 设 border-box 却漏掉 `input`。

### 栅格系统的真相：border-box 是所有栅格库的地基

如果你用过 Bootstrap、或者看过它的源码，会发现它第一行几乎永远是那个全局 `box-sizing` 复位。这不是巧合。

栅格系统的核心逻辑是"把一行等分成 12 份，每列用百分比占位，列之间用 padding 做 gutter（列间距）"：

```css
.row {
  width: 100%;
}
.col-6 {
  width: 50%;              /* 占 6/12 = 一半 */
  padding: 0 15px;         /* 列间距 gutter */
  box-sizing: border-box;  /* ✅ 没有这行，两个 50% + 30px 就溢出了 */
}
.col-4 {
  width: 33.333%;
  padding: 0 15px;
  box-sizing: border-box;
}
```

**如果栅格列用的是 content-box，那么"12 等分"的数学就彻底崩了**——每一列的 padding 都会往外撑，`50% + 50%` 会溢出换行，`33.333% × 3` 也会溢出。栅格系统能够成立，靠的就是 border-box 让 padding 从"外扩"变成"内缩"，百分比宽度才守得住。

所以下次你在任何 CSS 框架的 `reset.css` 或 `base.css` 顶部看到那三行 `*` 选择器，你就知道：**这不是洁癖，是"百分比布局"成立的前提条件。**

### `min-width` / `max-width` 和 box-sizing 的关系

还有一个容易混的点：`min-width`、`max-width` 是"下限/上限"，它们和 `width` 一样，也受 `box-sizing` 影响。

在 content-box 下，`max-width: 300px` 限制的是**内容区**不超过 300px，加上 padding 后整体仍会超过 300px；在 border-box 下，`max-width: 300px` 限制的就是**整个盒子**不超过 300px。

这意味着：border-box 下 `max-width: 100%` 是一个很有用的写法——"让这个盒子最多不超过父容器宽度"，配合 `padding` 也不会溢出。而 content-box 下 `max-width: 100%` 加了 padding 后照样会溢出父容器。又是一个"border-box 才符合直觉"的例证。

### 行内元素的盒模型是另一套

上面讲的都是**块级盒子**。行内元素（`<span>`、`<a>`、`<em>`）的盒模型要"另算"：

```css
.inline {
  width: 200px;        /* ❌ 对行内元素无效 */
  height: 100px;       /* ❌ 对行内元素无效 */
  padding: 20px;       /* ✅ 水平方向有效，垂直方向会"溢出"但不占布局高度 */
  margin: 20px;        /* ⚠️ 水平方向有效，垂直方向无效 */
  background: #fdecec;
}
```

行内元素的 `width`/`height` 直接被忽略，`padding`/`margin` 只在**水平方向**真正影响布局，垂直方向虽然视觉上有背景，但**不占高度**、也不影响行高。

这不是 bug，是 IFC（1.2 会讲）的规则：**行内元素的尺寸由内容（文字）决定，不由 `width`/`height` 决定。** 想让它尊重宽高，就把它变成 `display: inline-block`（既排成一行、又尊重宽高），或者干脆用 Flex 布局。

> 一句话记住它：**`width` 默认量的是内容区（content-box），加了 padding 和 border 就会往外撑大；`box-sizing: border-box` 让 `width` 变成"整个盒子的宽度"，符合直觉，所以全局强制它是标配。**

## 1.2 格式化上下文：那堵看不见的"隔离墙"

先给一个会让你"哦"一下的结论：**CSS 里没有"这个元素和那个元素"的绝对位置，只有"这个元素属于哪个格式化上下文，在上下文里排第几"。**

浏览器渲染页面时，不是把每个元素独立地摆到一个像素坐标上，而是把页面划分成若干个**格式化上下文**（Formatting Context），每个上下文是一个独立的排版单元，上下文内部的元素按一套规则排布，上下文与上下文之间互不干扰。

最常见的两种：

| 上下文 | 全称 | 里面排什么 | 一句话 |
|---|---|---|---|
| **BFC** | Block Formatting Context（块级格式化上下文） | 块级盒子，自上而下堆叠 | 一个块级"房间" |
| **IFC** | Inline Formatting Context（行内格式化上下文） | 行内盒子，自左而右排列 | 一行"文字流" |

整个页面根元素 `<html>` 本身就是一个天然的 BFC，这是"根 BFC"。当你在某个元素上触发一个新的 BFC 时，你就等于**在这个元素内部又开了一个独立的房间**。

### 先理解"匿名块盒"：BFC 为什么是"房间"而不是"元素"

看一段你在任何页面里都会遇到的 HTML：

```html
<div class="box">
  这是一段文字
  <p>这是一个段落</p>
  这又是另一段文字
</div>
```

`.box` 里混着"裸文字"和块级 `<p>`。浏览器渲染时，会把那些**没有包在任何块级元素里的裸文字**，自动包进一个你看不见的、匿名的块级盒子（anonymous block box），再和 `<p>` 一起参与块级堆叠。

这就是"格式化上下文"存在的原因：**浏览器需要一个统一的单位来"装"所有内容。** 你的 HTML 可以随便写（文字、标签乱混），但渲染引擎必须先把它归类成"块级盒子"和"行内盒子"，才能套用排版规则。BFC 就是这个"归类 + 排布"的容器。

### 这堵"隔离墙"隔绝的是三样会"穿透"的东西

理解 BFC 的全部价值，就是理解它挡住了哪三样"正常情况下会穿透元素边界"的东西。

#### 价值一：BFC 能让父容器"包住"浮动子元素（解决高度塌陷）

第 00 章讲过 `float` 会塌陷，这里我们讲**为什么 BFC 能修**。

默认情况下，父容器在"根 BFC"里排布，它计算自己高度时只认**在正常流里的块级子元素**，浮动的子元素"抽离"出去了，父容器看不到它，高度就塌了：

```html
<div class="parent">
  <div class="child">我在浮动</div>
</div>
```

```css
.parent {
  border: 2px solid #e5484d;
  /* 默认不创建 BFC，高度塌陷为 0 */
}

.child {
  float: left;
  width: 100px;
  height: 60px;
  background: #e5484d;
}
```

渲染效果：`.parent` 的红框高度是 0，只剩上下两条边贴在一起，`.child` 从框里"漏"了出去。

现在给父容器**创建一个 BFC**，同样的 HTML：

```css
.parent {
  border: 2px solid #12a150;
  overflow: hidden;   /* ✅ 触发 BFC */
}

.child {
  float: left;
  width: 100px;
  height: 60px;
  background: #12a150;
}
```

渲染效果：`.parent` 的绿框**包住了** `.child`，高度恢复正常。

为什么？这是规范明确写的规则：**BFC 在计算自身高度时，会把内部的浮动元素也计入。** 换句话说，普通块容器"看不见"浮动子元素，而 BFC"看得见"。你创建 BFC 那一刻，父容器就从"盲人"变成了"能看见浮动"。

#### 价值二：BFC 能阻止垂直外边距合并

一句话剧透：**两个相邻块元素的外边距会合并取大值，但如果其中一个被 BFC 隔开了，合并就不会发生。** 细节放到 1.3 展开，这里先记住"BFC 的墙能挡住 margin 穿透"这个能力。

#### 价值三：BFC 内部不会与外部浮动重叠（两栏布局的由来）

```html
<div class="wrap">
  <div class="sidebar">侧边栏（浮动）</div>
  <div class="main">主内容区</div>
</div>
```

```css
.sidebar {
  float: left;
  width: 200px;
  height: 400px;
  background: #fdecec;
}

.main {
  /* 默认不创建 BFC：文字会钻进 sidebar 右侧的空隙里 */
  background: #e8f7ee;
}
```

默认情况下，`.main` 的文字会**绕过**浮动的 `.sidebar`，钻进它右边的空隙（这就是 `float` 的"文字环绕"本职）。

但如果你要的是"主内容区整体和侧边栏并排，互不重叠"，就给 `.main` 创建 BFC：

```css
.main {
  overflow: hidden;   /* ✅ 触发 BFC，整块右移，不与 float 重叠 */
  background: #e8f7ee;
}
```

渲染效果：`.main` 变成一整块，左边顶着 `.sidebar`，右边占满剩余空间，内部文字不再绕进去。**这是最经典的"左定宽 + 右自适应"两栏布局的原理**（现代我们直接用 Flex/Grid，但理解它的根，你才知道为什么 Flex 里不存在这个坑）。

### 根元素本身就是 BFC：为什么"最外层"天然有墙

你可能会想：既然 BFC 这么好，那 `<html>` 是不是一个 BFC？

**是的，`<html>`（根元素）天然就是一个 BFC**，这叫"根 BFC"。这解释了一个你可能早就见过、但没细想的现象：**为什么 `body` 里的内容，从来不会和页面顶部的浏览器默认间距、或者别的页面"互相穿透"**——因为根 BFC 就是最外层那堵墙，所有内容都关在它里面。

它也解释了为什么"外边距合并"在页面最外层会被兜住：`body` 的第一个子元素如果设了 `margin-top`，这个 margin 会一路合并到 `body` 甚至 `html` 的 margin 上，但**不会穿透到 `<html>` 之外**——因为根 BFC 的边界就是文档的边界，墙外没有东西可穿透了。

### 一个对照实验：把 BFC 的三个价值放在一起看

为了让你一次看清 BFC 的"墙"到底挡了什么，这里放一个可复现的对照：

```html
<div class="group">
  <!-- 组 1：不建 BFC，塌陷 + 合并都发生 -->
  <div class="plain">
    <div class="floater"></div>
  </div>
  <!-- 组 2：建 BFC，塌陷和合并都被挡住 -->
  <div class="bfc">
    <div class="floater"></div>
  </div>
</div>
```

```css
.plain {
  border: 2px solid #e5484d;   /* 普通容器：红框，高度塌成 0 */
}
.bfc {
  display: flow-root;           /* ✅ 创建 BFC：绿框，包住浮动 */
  border: 2px solid #12a150;
}
.floater {
  float: left;
  width: 80px;
  height: 50px;
  background: #ccc;
}
```

渲染效果：`plain` 的红框塌成一条线，`bfc` 的绿框正常包裹住浮动子元素。**同样一个浮动子元素，放进 BFC 和放进普通容器，父容器的高度天差地别——这就是"墙"的意义。**

### 触发 BFC 的方式有哪些

| 触发方式 | 副作用 | 评价 |
|---|---|---|
| `overflow: hidden / auto / scroll`（非 `visible`） | 会裁剪溢出内容、可能冒出滚动条 | 历史最常用，但**有副作用** |
| `display: flow-root` | **无任何副作用** | **现代正解** |
| `display: inline-block` / `table-cell` / `table-caption` | 改变元素本身性质 | 会连排版一起变 |
| `float: left / right` | 脱离文档流 | 用 A 坑修 B 坑 |
| `position: absolute / fixed` | 脱离文档流 | 同上 |

### 为什么 `display: flow-root` 是"专门为创建 BFC 而生"的

看上面这张表，你会发现一个尴尬的事实：**在 `flow-root` 出现之前，没有任何一个"只为创建 BFC"的干净办法。**

- 想修高度塌陷，最常用的是 `overflow: hidden`——但它的本职是"裁剪溢出"，你只是想"包住浮动"，却顺带禁掉了"溢出可见"。哪天你想让 `.main` 里放一个故意超出边界的装饰（比如一个角落的角标 `position: absolute; right: -10px`），`overflow: hidden` 会一刀把它裁掉，你还得再想办法。
- 想用 `display: inline-block` 触发 BFC，结果元素从"块级"变成"行内块级"，width、margin 的行为全变了。
- 想用 `float` 触发，那更是拿"高度塌陷的元凶"去修"高度塌陷"。

于是 2018 年前后，W3C 干脆给 `display` 加了一个新值 **`flow-root`**：

```css
.parent {
  display: flow-root;   /* ✅ 创建 BFC，仅此而已，没有别的副作用 */
}
```

**`flow-root` 的字面意思就是"根流"**——它让元素像根元素 `<html>` 一样，成为一个独立的块级格式化上下文的根。它**唯一做的事就是创建 BFC**：

- 不裁剪溢出（不像 `overflow: hidden`）
- 不改变元素是块级还是行内的性质（不像 `inline-block`）
- 不脱离文档流（不像 `float` / `position`）

现代浏览器（2020 年后所有主流浏览器）全都支持。**所以今天要创建 BFC，`display: flow-root` 是唯一应该用的答案**，`overflow: hidden` 只在你"本来就想裁剪溢出"时才顺手用。

### 顺带说清楚 IFC：为什么 `vertical-align` 这么玄

IFC（行内格式化上下文）是"一行文字"的排版规则。块级盒子里没有块级子元素时，就形成了一个 IFC，里面的文字、`<span>`、`<img>`、`<em>` 这些**行内级盒子**按顺序排成一行，行与行之间组成行盒（line box）。

IFC 里最反直觉的是**基线（baseline）对齐**：

```html
<div class="line">
  <span class="big">大</span>
  <span class="small">小</span>
</div>
```

```css
.big   { font-size: 40px; }
.small { font-size: 14px; }
```

你会发现"大"字和"小"字**并没有底部对齐**，小字像是"飘"在大字中段偏下的位置。因为行内元素默认 `vertical-align: baseline`——按**文字基线**对齐，而不是按盒子底部对齐。

这就是为什么很多前端觉得 `vertical-align` "调不动"：它不是"让元素在容器里垂直居中"，而是**"让这个行内盒子的哪条线，去对齐同行其他盒子的哪条线"**，作用对象和坐标系都跟你想的不一样。

想真正垂直居中一个行内元素，要么给它所在容器换 `flex`，要么用 `vertical-align: middle` 并理解它对齐的是"父元素基线 + 半个 x-height"——这套东西细节属于排版排版（typography）领域，这里你只需要记住结论：**IFC 是"文字世界"的规则，跟"块级布局"是两套坐标系，别混着用。**

> 一句话记住它：**BFC 是一堵"隔离墙"，墙内墙外的浮动、外边距互不穿透；创建 BFC 用 `display: flow-root`（无副作用），`overflow: hidden` 是带副作用的旧办法。**

## 1.3 外边距合并（margin collapsing）：20px + 30px = 30px

先说结论：**垂直方向相邻的两个 `margin` 不会相加，而是"合并取较大值"。这不是 bug，是规范白纸黑字写死的规则。**

看一段会吓到新手的代码：

```html
<div class="a">A</div>
<div class="b">B</div>
```

```css
.a {
  margin-bottom: 20px;
  background: #fdecec;
}
.b {
  margin-top: 30px;
  background: #e8f7ee;
}
```

你按命令式思维想：A 的下边距 20px，B 的上边距 30px，中间的间隙应该是 20 + 30 = **50px**。

但浏览器渲染出来，A 和 B 之间的间距是 **30px**——取两者较大的那个，另一个"消失"了。

### 什么情况下会合并

规范规定了三类合并场景，全是**垂直方向**（水平方向的 margin 从不合并）：

**场景一：相邻兄弟元素。** 上一个元素的下边距，和下一个元素的上边距，合并。就是上面这个例子。

**场景二：父元素与第一个/最后一个子元素。** 父元素没有 border、padding、行内内容等"隔离物"时，子元素的 `margin-top` 会"顶穿"父元素，变成父元素自己的 `margin-top`：

```html
<div class="parent">
  <div class="child">子元素</div>
</div>
```

```css
.parent {
  background: #fdecec;
  /* 没有 padding、border，也没有内容把它和孩子隔开 */
}
.child {
  margin-top: 30px;   /* ❌ 这个 margin 会"漏"到 parent 外面去 */
}
```

渲染效果：你以为 `.child` 会在 `.parent` 内部往下缩 30px，结果却是 `.parent` 和 `.child` 一起整体往下掉了 30px——子元素的 margin 穿透了父元素，合并到了父元素的外面。这正是"父子合并"。

**场景三：空块自身合并。** 一个没有高度、没有 border/padding、没有内容的空元素，它的 `margin-top` 和 `margin-bottom` 会合并成一个：

```html
<div class="a">A</div>
<div class="empty"></div>
<div class="b">B</div>
```

```css
.a    { margin-bottom: 20px; }
.empty { margin: 30px 0; }   /* 空的：上下 margin 会合并成 30px */
.b    { margin-top: 40px; }
```

这里 `.empty` 是个空块，它自己的 `30px + 30px` 先合并成一个 30px，再和上下邻居继续合并。这个场景少见，但它说明了一个规律：**合并会"传染"，一个空隙处只会留下一个最终值。**

### 为什么规范要这么设计

**为了排版美观，让段落间距不会翻倍。**

想象一篇文章，每个 `<p>` 段落都写了 `margin: 1em 0`（上下各 1em）。如果没有合并，两个段落之间的间距会是"上段的下 1em + 下段的上 1em = 2em"，**翻倍**。而段首段尾需要的间距其实是统一的 1em。

外边距合并让"相邻段落间的间距"正好等于单边 margin，排版才紧凑、匀称。**它解决的是"重复边距叠加导致间距失控"这个排版问题。**

所以记住：**合并不是 bug，是排版学的设计。** 你崩溃是因为你用"命令式思维"（我写了两条命令，效果就该叠加）去套"声明式规则"（浏览器有一套管 margin 的合并规则）。

### 两个容易忽略的细节

**细节一：负 margin 的合并规则是"取绝对值较大者"。**

```css
.a { margin-bottom: 20px; }
.b { margin-top: -30px; }   /* 负值 */
```

正 20 和负 30 合并，结果是 `-10px`（两个值相加）。多个 margin 合并时，浏览器取"最大的正数 + 最小的负数"之和。结论：**有正有负时，最终值是两个最极端值的代数和**，不是简单取大。

**细节二：只有"正常文档流"里的 margin 才合并。**

浮动元素、绝对定位元素（`position: absolute/fixed`）已经从文档流里抽离，它们的外边距**从不和别人合并**。flex/grid 容器的子项之间也**不合并**（规范明确排除）。所以你会看到：同一段布局，用 float 排版时 margin 会"偷偷合并"，换成 flex 后间距又"突然变大了一倍"——不是 flex 出 bug，是 flex 里根本没合并这回事。

### 怎么破

关键点：**外边距合并只发生在"同一个 BFC 里的、正常文档流中的、垂直相邻"的 margin 之间。** 只要打破其中任何一个条件，合并就不发生。

**破法一：让父元素创建 BFC。** 回到场景二的父子合并，给父元素加 `display: flow-root`：

```css
.parent {
  display: flow-root;   /* ✅ 创建 BFC，子元素的 margin 不再穿透 */
  background: #fdecec;
}
.child {
  margin-top: 30px;
}
```

渲染效果：`.child` 现在老老实实地在 `.parent` **内部**往下缩 30px，不再往外漏。因为 BFC 是一堵墙，墙内的 margin 传不出去。

**破法二：给父元素加"隔离物"。** 哪怕 1px 的 padding 或 border，都能阻止父子合并：

```css
.parent {
  padding-top: 1px;   /* ✅ 任意一点 padding 都能挡住宿命 */
}
```

**破法三：用 Flex / Grid 容器。** 这是现代最常用的解法，也解释了为什么第 00 章说"用了 Flex/Grid，一整类坑直接消失"：

```css
.parent {
  display: flex;
  flex-direction: column;   /* ✅ flex 容器里，子项 margin 不合并 */
  gap: 20px;                /* 间距交给 gap 统一管理 */
}
```

**为什么 flex/grid 里不合并？** 因为规范明确写着：**flex 容器和 grid 容器的子项之间，不发生外边距合并。** 在 Flex/Grid 布局里，"间距"这个职责已经交给 `gap` 去统一管理了，margin 合并这套"段落排版规则"不该、也不需要再介入。

这也是一条重要心法：**margin 是"文档流时代"排版间距的工具，进入 Flex/Grid 后，间距请优先用 `gap`，margin 留给"组件与组件之间"这种文档流场景。**

### 为什么 `margin: auto` 的水平居中从不"合并"

你可能用过这个经典的水平居中写法：

```css
.center {
  width: 400px;
  margin-left: auto;    /* 左右都是 auto */
  margin-right: auto;
}
```

这里的 `margin: auto` 意思是"剩余空间由浏览器自动分配"——左右两边均分，于是元素居中。

**注意：这个 `auto` 从来不会触发"外边距合并"。** 因为合并的前提是"两个具体的长度值相邻"，而 `auto` 不是一个长度值，它是"交给浏览器算"。浏览器在分配剩余空间时，压根不走"合并"那套逻辑。

这也印证了一个规律：**`margin: auto` 是"分配剩余空间"，`margin: 20px` 是"声明固定间距"**——前者是"请帮我算"，后者是"就这个值，可能要跟邻居合并"。两条路完全不同。

> 一句话记住它：**垂直相邻的 margin 会合并取大值（段落排版的刻意设计）；BFC、padding、flex/grid 都能打破它，而 flex/grid 里本来就不该再用 margin 管间距，交给 `gap`。**

## 1.4 层叠上下文与 z-index：为什么 `9999` 有时候按不住

先给结论：**`z-index` 不是全局的"谁大谁在上"，而是"在同一个层叠上下文里，谁大谁在上"。元素永远出不了它所在的那个层叠上下文。**

### 先看两个经典的"失灵"现场

**现场一：`z-index` 根本不生效。**

```html
<div class="box">普通盒子</div>
<div class="overlay">盖住它</div>
```

```css
.box {
  width: 200px;
  height: 100px;
  background: #fdecec;
}
.overlay {
  width: 200px;
  height: 100px;
  background: #2f6fed;
  z-index: 9999;   /* ❌ 写了，但一点用没有 */
}
```

渲染效果：`.overlay` 并没有盖到 `.box` 上面，两个盒子还是按文档顺序先后排列。你的 `z-index: 9999` 像是被浏览器忽略了。

**原因**：`z-index` 只对**定位元素**（`position` 是 `relative/absolute/fixed/sticky` 之一）生效，对 `position: static` 的普通元素无效。`.overlay` 没设 `position`，它是 static，`z-index` 直接被无视。（例外：flex/grid 容器的**子项**即使不定位，`z-index` 也生效，但普通文档流里不行。）

**修法**：给 `.overlay` 加一个非 static 的定位：

```css
.overlay {
  position: relative;   /* ✅ 先让它成为定位元素 */
  z-index: 9999;
}
```

**现场二：`z-index: 9999` 被一个 `z-index: 1` 的按住了。**

这是更让人崩溃的一个：

```html
<div class="parent-a">
  <div class="child-a">我 z-index 是 9999</div>
</div>
<div class="parent-b">
  <div class="child-b">我 z-index 是 1</div>
</div>
```

```css
.parent-a {
  position: relative;
  z-index: 1;             /* 父 A 的层叠上下文层级是 1 */
}
.child-a {
  position: relative;
  z-index: 9999;          /* ❌ 子 A 再大也没用 */
  background: #fdecec;
}

.parent-b {
  position: relative;
  z-index: 2;             /* 父 B 的层叠上下文层级是 2 */
}
.child-b {
  position: relative;
  z-index: 1;             /* 子 B 只有 1 */
  background: #e8f7ee;
}
```

渲染效果：`child-b` 盖在 `child-a` 上面，尽管 `child-a` 的 z-index 是 9999、`child-b` 只有 1。

**原因**：`z-index` 只在**同一个层叠上下文**里比较。`parent-a` 和 `parent-b` 各自因为"定位 + z-index"创建了自己的层叠上下文，于是浏览器先比较两个**父元素**（1 和 2，parent-b 赢），父元素谁在上，它内部的子元素**整体**就在上——子元素的 z-index 再高，也高不出它所在的父层叠上下文。

**这就是"层叠上下文"的本质：它是一个封闭的盒子，内部的 z-index 排序对外界不可见。** 外面只能看到这个盒子的层级，看不到盒子内部怎么排。

### 层叠上下文是怎么被创建出来的

创建层叠上下文的方式远不止"定位 + z-index"。以下属性**只要满足条件，都会创建一个层叠上下文**：

| 触发条件 | 说明 |
|---|---|
| `position: relative/absolute/fixed/sticky` **且** `z-index` 不是 `auto` | 最经典的创建方式 |
| `position: fixed` / `sticky` | 即使 z-index 是 auto，多数浏览器也创建 |
| `opacity < 1` | 一个半透明元素自己就是层叠上下文 |
| `transform` / `filter` / `perspective` 等非 `none` | 用了 3D/滤镜就创建 |
| `will-change: transform` 等 | 声明了就会提前创建 |
| `mix-blend-mode` / `isolation: isolate` | 混合模式/显式隔离 |

**这一条是无数前端"调 z-index 调到怀疑人生"的根源**：你以为自己只给元素写了个 `transform` 动画，结果它悄悄创建了一个层叠上下文，把内部所有子元素的 z-index 都"锁死"在了这个新上下文里，原本能浮到页面最顶层的弹窗，突然被自己的父容器压住了。

一个典型翻车现场：你给一个卡片加了 `opacity: 0.9`（想做个半透明效果），结果卡片里的"删除确认弹窗"（`position: fixed; z-index: 9999`）再也盖不住页面上的其他元素了——因为 `opacity < 1` 让卡片成了一个新层叠上下文，弹窗被"关"进了卡片这个层级里，而卡片本身的层级又不高。

**这就是为什么要认识 `isolation: isolate`**：它是个"只创建层叠上下文、不改任何视觉"的属性。当你需要"把一个元素单独隔成一层，但不想动它的 opacity/transform/z-index"时，`isolation: isolate` 是干净的解法：

```css
.card {
  isolation: isolate;   /* ✅ 显式创建一个独立的层叠上下文，无视觉副作用 */
}
```

### 层叠顺序：同一层叠上下文内部的七层

在一个层叠上下文内部，元素按下面这个**从低到高**的顺序叠放（每一层内部再各自排序）：

```text
1. 层叠上下文的背景和边框（最底层）
2. 负 z-index 的定位元素
3. 普通文档流里的块级盒子
4. 浮动元素（float）
5. 普通文档流里的行内级盒子
6. z-index: 0 或 auto 的定位元素
7. 正 z-index 的定位元素（最顶层）
```

**背下这张表的意义**：它解释了两个高频现象——

- **为什么"负 z-index 的元素会钻到背景下面"**：第 2 层（负 z-index 定位元素）在根层叠上下文的背景（第 1 层）**之上**，但如果你给一个"正常流块级盒子"设了背景，负 z-index 元素可能跑到它下面。具体谁在谁下，取决于它们各属第几层。
- **为什么"浮动元素盖不住行内文字"**：浮动的 `<img>` 是第 4 层，而文字是第 5 层，所以文字永远在浮动图片的上方（这正是"文字环绕图片"且文字不被图片遮住的原理）。

但比背表更重要的是那条总原则：**先确认两个元素是不是在同一个层叠上下文里。不在同一个，谁大谁小根本没得比，直接比它们各自的"父上下文"谁高。**

### 一个例外：flex/grid 子项的 z-index 不需要定位

前面说"z-index 对 static 元素无效"，但有一个**重要例外**：**flex 容器或 grid 容器的子项，即使 `position` 是 `static`，`z-index` 也照样生效。**

```html
<div class="flex">
  <div class="item">一号</div>
  <div class="item top">二号</div>
</div>
```

```css
.flex {
  display: flex;
}
.item {
  width: 100px;
  height: 100px;
  background: #fdecec;
}
.top {
  z-index: 1;            /* ✅ 没有 position，但因为是 flex 子项，z-index 生效 */
  background: #2f6fed;
}
```

渲染效果：`top` 这个 flex 子项盖在 `item` 上面，尽管它没设 `position`。

原因：规范规定，flex/grid 子项本身是"弹性项/网格项"，它们的层叠规则**不依赖定位**，`z-index` 直接参与排序。这个例外在现代布局里很常用（比如轮播图、卡片堆叠），也解释了为什么有些新手"明明没定位，z-index 却生效了"——因为他没意识到元素在 flex 里。

### 遇到"z-index 不听话"，按这个顺序排查

别上来就无脑加 `!important`，按下面四条从上往下查：

1. **它定位了吗？** 不是 flex/grid 子项、又不是定位元素，`z-index` 直接无效。
2. **它在哪个层叠上下文里？** 它和"被它盖的元素"是否同属一个父上下文？不在同一个，比的是父级。
3. **它的祖先有没有 `opacity` / `transform` / `filter`？** 这些会悄悄创建新的层叠上下文，把它的层级"关"进去。
4. **它的 z-index 值本身合理吗？** 同层内确实是"大者在上"，确认你要盖的东西 z-index 到底是多少。

> 一句话记住它：**`z-index` 只在同一个层叠上下文里比较；元素出不了它所在的层叠上下文。调 z-index 没反应，先查两件事——它定位了吗？它的父元素是不是创建了更低的层叠上下文？**

## 1.5 定位（position）：五个值，锚定五种不同的东西

先给一张总表，后面逐个讲"锚定谁、脱离不脱离流"：

| 值 | 锚定谁 | 脱离文档流吗 | 一句话 |
|---|---|---|---|
| `static` | 不偏移，待在正常流里 | 否 | 默认状态 |
| `relative` | **自己原本的位置** | 否（原位保留） | 挪自己，但原位置还占着 |
| `absolute` | **最近的定位祖先**（没有就是初始包含块） | 是 | 从文档流里抽走，锚到祖先 |
| `fixed` | **视口（viewport）** | 是 | 永远固定在屏幕某个位置 |
| `sticky` | **滚动容器**（阈值内像 relative，超过像 fixed） | 否（原位保留） | 滚到阈值就"吸"住 |

### `static` 与 `relative`：不脱离流，偏移是"障眼法"

`static` 是默认值，元素就在正常文档流里，`top/left/z-index` 对它全都不生效。

`relative` 的关键认知是：**它偏移的是"视觉位置"，不是"文档流位置"。**

```html
<div class="parent">
  <div class="box">relative 盒子</div>
  <div class="next">下一个盒子</div>
</div>
```

```css
.box {
  position: relative;
  top: 20px;
  left: 20px;          /* 视觉上往右下挪了 20px */
  background: #fdecec;
}
.next {
  background: #e8f7ee;
}
```

渲染效果：`.box` 视觉上往右下挪了 20px，**但它原本的位置仍然空着占位**，`.next` 不会顶上来。这就是"脱离不脱离流"最直观的区别——relative 只是"画在了别处"，流里的坑还留着。

relative 最常用的场景，其实是**给 absolute 子元素当"锚点"**（见下一节），或者做 1px 级别的微调。

### `absolute`：包含块是谁，这个问题的答案决定了它飞去哪

`absolute` 会**从文档流里抽离**（原来位置不留坑），然后锚定到它的**包含块（containing block）**上，用 `top/right/bottom/left` 定位。

**包含块是谁？** 这是 absolute 最重要的一条规则：

> **`absolute` 元素的包含块，是离它最近的、`position` 非 `static` 的祖先元素。**

如果没有这样的祖先，包含块就是"初始包含块"（通常是 `<html>`，尺寸等于视口，随页面滚动）。

看代码：

```html
<div class="ancestor">
  <div class="child">我锚定祖先</div>
</div>
```

```css
.ancestor {
  position: relative;   /* 关键：作为包含块 */
  width: 300px;
  height: 200px;
  background: #fdecec;
}
.child {
  position: absolute;
  top: 0;
  right: 0;             /* 锚定到 ancestor 的右上角 */
  background: #2f6fed;
  color: #fff;
}
```

渲染效果：`.child` 落在 `.ancestor` 的右上角。**因为它找到了最近的定位祖先 `.ancestor`。**

如果你把 `.ancestor` 的 `position: relative` 删掉，`.child` 会一路向上找，找不到定位祖先，最终锚定到 `<html>`，于是它就会飞到**页面**的右上角，而不是 `.ancestor` 的右上角。

**这是"absolute 飘了"最常见的根因**：你忘了给它的祖先设 `position: relative`，结果它锚到了视口。所以经典套路是——**父元素 `position: relative`，子元素 `position: absolute`**，父当锚、子定位。

另一个反直觉点：absolute 元素如果**四个方向都没指定**（`top/right/bottom/left` 全是 `auto`），它不会飞走，而是停留在"假如它还在文档流里应该待的那个位置"，只是不占位了。所以"只写 `position: absolute` 不写方向"时，元素往往还待在原地附近，只是流里空了。

**同时指定 `top` 和 `bottom`（不设 height）** 时，元素会被"上下拉伸"到两者之间；同理 `left` + `right` 会水平拉伸。这是 absolute 一个容易被忽略的"弹性"能力。

**而这个"拉伸 + `margin: auto`"的组合，能实现绝对定位元素的水平垂直居中**（第 00 章提过的十几种居中写法之一）：

```html
<div class="stage">
  <div class="dialog">居中弹窗</div>
</div>
```

```css
.stage {
  position: relative;
  width: 400px;
  height: 300px;
  background: #f0f0f0;
}
.dialog {
  position: absolute;
  top: 0;
  right: 0;
  bottom: 0;
  left: 0;             /* 四个方向都钉死，元素被拉伸 */
  width: 200px;
  height: 120px;       /* 但给了固定宽高，于是不再拉伸 */
  margin: auto;        /* ✅ 剩余空间四方均分 → 居中 */
  background: #2f6fed;
  color: #fff;
}
```

渲染效果：`.dialog` 精确地水平垂直居中在 `.stage` 里。原理：四个方向都设为 0 意味着"元素想被拉伸填满"，但你又给了固定 `width`/`height` 阻止了拉伸，这时多出来的空间就由 `margin: auto` 均分——四个方向都 auto，就是四方居中。

这个写法比 `transform: translate(-50%, -50%)` 更"干净"（不依赖 transform，不触发层叠上下文），但只在"固定宽高 + 定位祖先"时好用；元素尺寸不确定时，还是 `place-items: center`（Grid）最省事。

### `fixed`：锚定视口，滚动也不动

`fixed` 也脱离文档流，但它锚定的是**视口（viewport）**——就是浏览器窗口当前可见的那个矩形区域。

```css
.chat-button {
  position: fixed;
  right: 24px;
  bottom: 24px;         /* 锚定视口右下角 */
  z-index: 10;
  width: 56px;
  height: 56px;
  border-radius: 50%;
  background: #2f6fed;
}
```

渲染效果：这个"客服按钮"固定悬浮在窗口右下角，**页面怎么滚它都不动**。

`fixed` 有一个容易被忽略的坑：**如果它的某个祖先有 `transform`、`filter`、`perspective` 等属性（即创建了新的包含块），`fixed` 就不再锚定视口，而是锚定那个祖先**，行为瞬间变成"绝对定位"。这是"fixed 突然不 fixed 了"的经典原因。现代浏览器里 `transform` 会让后代 `fixed` 的包含块变成这个祖先：

```css
.ancestor {
  transform: translateZ(0);   /* ❌ 只是想开个 GPU 加速，结果 fixed 后代锚定它了 */
}
.child {
  position: fixed;            /* 现在不是相对视口，而是相对 .ancestor 了 */
  top: 0;
}
```

### `sticky`：滚到阈值前像 relative，滚过阈值后像 fixed

`sticky` 是最晚出现、也最容易被误解的一个。它**不脱离文档流**（原位保留），行为是：

> **在滚动容器里，元素原本该在某个位置；当滚动让它快要离开视野时，它会被"吸"在指定阈值上，不再继续滚走；滚回阈值内时又恢复原位。**

看一个导航栏吸顶的经典例子：

```html
<div class="content">
  <p>一些占位内容……（很长，产生滚动）</p>
  <div class="sticky-bar">我要吸顶</div>
  <p>更多占位内容……</p>
</div>
```

```css
.sticky-bar {
  position: sticky;
  top: 0;               /* 滚到离视口顶部 0px 时吸住 */
  background: #2f6fed;
  color: #fff;
}
```

渲染效果：`.sticky-bar` 初始待在它文档流的位置；你往下滚动，它升到离视口顶部 0px 时，就**停在顶部不再往上滚**，像 fixed 一样；滚回它原来的位置上方时，它又落回原位。

**理解 sticky 的三个关键点：**

1. **它需要"滚动容器"。** sticky 是在某个可滚动的容器里吸附的，通常是整个页面（视口），也可以是 `overflow: auto` 的内层容器。
2. **`top: 0` 是"阈值"，不是"初始位置"。** 它不是说元素贴在顶部 0px 处，而是"当元素距离视口（或滚动容器）顶部不足 0px 时，吸在 0px 处"。
3. **sticky 只在它父元素范围内生效。** 元素最多只能在它的父容器内滑动，滑出父容器边界就不会再吸。这是"sticky 突然失效"的常见原因——父容器不够高，或者父容器有 `overflow: hidden` 把它"关"住了。

**sticky 的本质 = relative + fixed 的杂交**：阈值内它是 relative（待在文档流里），超过阈值它是 fixed（吸在阈值上），但又被限制在父容器内。

### sticky 的进阶：吸附一个"侧边栏"

`sticky` 不只用于吸顶导航，还能做"跟随滚动的侧边栏"——这是它最漂亮的实战场景：

```html
<div class="layout">
  <aside class="side">侧边栏（很长或很短都行）</aside>
  <main class="content">主内容（很长，产生滚动）……</main>
</div>
```

```css
.layout {
  display: flex;
  align-items: flex-start;   /* 关键：让 aside 不拉伸成和 content 一样高 */
}
.side {
  position: sticky;
  top: 20px;                 /* 距离视口顶部 20px 时吸附 */
  width: 200px;
}
.content {
  flex: 1;
  min-height: 2000px;        /* 让页面足够长，能滚动 */
}
```

渲染效果：当你往下滚动时，左侧的 `.side` 会在"距离视口顶部 20px"的位置停住，不再跟着滚走；而右侧的 `.content` 继续滚。侧边栏就实现了"吸附悬浮"。

**这里藏着 sticky 最容易踩的第二个坑**：`align-items: flex-start` 这行不能省。如果省了，flex 默认的 `align-items: stretch` 会把 `.side` 拉伸成和 `.content` 一样高（2000px），那 sticky 就"永远有地方待"，根本不会滚动吸附——因为 sticky 只在自己的父容器（这里是 `.layout`）范围内吸附，父容器被拉伸得和内容一样高，侧边栏自然全程都"在范围内"。

所以 sticky 侧边栏的经典结构是：**flex 容器 + `align-items: flex-start` 防止拉伸 + sticky 子项 `top: xx`。** 缺一个，吸附就失效。

> 一句话记住它：**`relative` 挪自己但留坑；`absolute` 锚定最近的定位祖先（没有就锚视口）；`fixed` 锚定视口；`sticky` 是"relative 到 fixed 的开关"，滚到阈值就吸住、但逃不出父容器。**

## 1.6 综合案例：用这套心智模型，排查一个"四连坑"的卡片列表

前面五节是分开讲的，但真实世界里它们会**同时**出现。这里放一个综合案例，把盒模型、外边距合并、包含块、层叠上下文串起来。

**需求**：做一个商品卡片列表。每个卡片有内边距、右上角一个"热卖"角标、卡片之间间距 16px、悬停时卡片放大。

先看一段"看起来都对"的代码：

```html
<div class="list">
  <div class="card">
    商品 A
    <span class="badge">热卖</span>
  </div>
  <div class="card">
    商品 B
    <span class="badge">热卖</span>
  </div>
</div>
```

```css
.list {
  width: 400px;
}
.card {
  width: 50%;
  padding: 20px;
  margin-bottom: 16px;
  background: #fdecec;
  transition: transform 0.2s;
}
.card:hover {
  transform: scale(1.05);      /* 悬停放大 */
}
.badge {
  position: absolute;           /* 角标绝对定位 */
  top: 0;
  right: 0;
  background: #e5484d;
  color: #fff;
}
```

这段代码至少藏着 **4 个坑**，我们一个个揪出来：

### 坑一：两个卡片不并排（盒模型）

`.card` 是 `width: 50%` + `padding: 20px`，在默认 content-box 下，每个卡片实际占 `50% + 40px`，两个加起来溢出，第二张卡片被挤到下一行。

**修**：全局 `box-sizing: border-box`，或给 `.card` 加 `box-sizing: border-box`。

### 坑二：卡片间距不是 16px（外边距合并）

两张卡片都 `margin-bottom: 16px`，但它们**垂直方向相邻**，外边距会合并，间距还是 16px 而不是 32px——这个场景里 16px 恰好是你想要的，所以暂时"没毛病"。但如果第二张卡片设了 `margin-top: 40px`，间距就会变成 40px（取大），而不是你以为的 16+40。

**修**：把 `.list` 改成 flex/grid 容器，间距交给 `gap: 16px`，让 margin 不再参与合并：

```css
.list {
  display: flex;
  gap: 16px;
}
```

### 坑三：角标飞到页面右上角（包含块）

`.badge` 是 `position: absolute`，但 `.card` 没有设 `position: relative`。于是角标一路向上找定位祖先，找不到，最终锚定到 `<html>`，**所有角标都堆到了页面右上角**，而不是各自卡片的右上角。

**修**：给 `.card` 加 `position: relative`，让它成为角标的包含块：

```css
.card {
  position: relative;   /* ✅ 让角标锚定在卡片内 */
}
```

### 坑四：悬停放大后，角标层级乱套（层叠上下文）

`.card:hover` 有 `transform: scale(1.05)`。**`transform` 会让卡片创建一个层叠上下文**。如果你之前给卡片或角标设过 z-index，现在它们全被"锁"进卡片这个新的层叠上下文里，可能导致角标盖不住/盖得过别的元素，行为和你预期的不一致。

**修**：理解这一点即可——悬停放大这个"看似纯视觉"的 transform，其实悄悄改变了层叠结构。如果你有复杂的 z-index 层级，避免在"承载了 z-index 关键元素"的容器上用 transform，或者统一用 `isolation: isolate` 显式管理层级。

### 四连坑的最终版

```css
*, *::before, *::after {
  box-sizing: border-box;          /* 修坑一 */
}
.list {
  display: flex;                    /* 修坑二：flex 子项不合并 margin */
  gap: 16px;
}
.card {
  position: relative;               /* 修坑三：成为角标包含块 */
  width: 50%;
  padding: 20px;
  background: #fdecec;
  transition: transform 0.2s;
}
.card:hover {
  transform: scale(1.05);           /* 坑四：认知到它会创建层叠上下文 */
}
.badge {
  position: absolute;
  top: 0;
  right: 0;
  background: #e5484d;
  color: #fff;
}
```

**这个案例的价值不在"背下这四行修复"，而在让你看到**：一个再普通不过的卡片列表，四个坑分别来自四套不同的规则层（盒模型、外边距、包含块、层叠上下文）。**你脑子里有这四套心智模型，排查时就能"按图索骥"**，而不是对着屏幕抓狂"为什么又不听话"。

## 1.7 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| `width: 300px` 却渲染成 342px | 元素比预期宽 | 默认 `content-box`，padding/border 在外面另加 | 全局 `box-sizing: border-box` |
| 两个 `width: 50%` 不并排、换行了 | 加了 padding 后 50%+50% 溢出 | content-box 下 padding 往外撑 | `border-box`，或改用 Flex/Grid |
| 父容器高度塌成 0 | `float` 子元素"漏"出父框 | 普通容器看不见浮动子元素 | 父容器 `display: flow-root`（或 `overflow: hidden`） |
| 子元素 `margin-top` 把父元素一起顶下去了 | 父子外边距合并穿透 | 父容器没有 border/padding 隔离 | 父容器 `display: flow-root` 或加 `padding-top: 1px` |
| 两元素垂直间距不是 20+30=50 | 间距是 30（取大） | 垂直外边距合并 | 用 flex/grid 容器 + `gap`，或创建 BFC |
| 行内元素设 `width/height` 没反应 | 尺寸不变 | 行内元素尺寸由内容决定 | 改 `display: inline-block` 或 flex |
| `z-index: 9999` 没用 | 元素没盖上去 | `position: static` 的元素 z-index 无效 | 先 `position: relative` 再设 z-index |
| `z-index: 9999` 被 `z-index: 1` 压住 | 高 z-index 反而在下 | 两者不在同一层叠上下文 | 提升**父级**层叠上下文，别只提子级 |
| 弹窗突然盖不住别人 | 之前好好的，加了 opacity 就乱 | `opacity < 1` 创建了新层叠上下文 | 用 `isolation: isolate` 或调整 DOM 层级 |
| `fixed` 元素不 fixed 了，跟着祖先滚 | 像 absolute 一样锚定祖先 | 祖先有 `transform`/`filter`，成了新的包含块 | 检查祖先是否创建包含块，或调整结构 |
| `sticky` 不吸附 | 元素直接滚走了 | 没设 `top` 阈值，或父容器太矮/有 `overflow: hidden` | 设 `top: 0`，并确认父容器高度与滚动容器 |
| `absolute` 元素飞到页面角落 | 没锚到预期祖先 | 最近的定位祖先不存在，锚到 `<html>` | 给预期祖先 `position: relative` |
| `overflow: hidden` 裁掉了角标 | 用 overflow 修 BFC，却裁了溢出装饰 | `overflow: hidden` 有裁剪副作用 | 改用 `display: flow-root` 创建 BFC |

## 1.8 本章小结

- **盒模型**：`width` 默认量内容区（content-box），padding/border 外扩；`box-sizing: border-box` 让 `width` 变成整个盒子宽度，是直觉且不翻车的选择，所以全局 `*, *::before, *::after { box-sizing: border-box }` 是标配。
- **格式化上下文**：BFC 是块级"隔离墙"，隔绝浮动、外边距穿透、浮动重叠；`display: flow-root` 是唯一"只为创建 BFC、无副作用"的现代正解，`overflow: hidden` 是带裁剪副作用的旧办法。
- **外边距合并**：垂直相邻 margin 合并取大值，是段落排版的刻意设计；BFC、padding/border、flex/grid 都能打破它；进了 flex/grid 就该用 `gap` 管间距。
- **层叠上下文**：`z-index` 只在同一层叠上下文里比较；元素出不了父层叠上下文；z-index 对 static 元素无效；`opacity < 1`、`transform` 等会悄悄创建层叠上下文。
- **定位**：`relative` 挪自己留坑、`absolute` 锚定最近定位祖先、`fixed` 锚定视口、`sticky` 是 relative/fixed 的滚动开关。
- **核心心法**：先想"元素属于哪个上下文、锚定谁、脱离不脱离流"，再写属性——布局问题都是这三问答错了，不是属性记少了。

## 1.9 动手练习

1. 一个 `width: 200px; padding: 0 30px; border: 10px solid` 的元素，在默认 `content-box` 下，实际占用的总宽度是多少？改成 `border-box` 后呢？

   <details><summary>参考答案</summary>

   content-box：`width(200) + padding 左右(60) + border 左右(20) = 280px`；内容区仍是 200px。

   border-box：总宽度就是 `width = 200px`；内容区被压缩为 `200 - 60 - 20 = 120px`。

   一句话：content-box 往外加，border-box 往里减。
   </details>

2. 父容器里有一个 `float: left` 的子元素，父容器高度塌了。请用**两种**方法修复，并说明为什么你更推荐其中一种。

   <details><summary>参考答案</summary>

   方法一：父容器 `overflow: hidden`——能修，但会裁剪溢出内容（副作用）。

   方法二：父容器 `display: flow-root`——只创建 BFC，无任何副作用。

   推荐方法二，因为它的语义就是"创建 BFC"，不夹带"裁剪"这种跟布局无关的副作用。
   </details>

3. A 元素 `margin-bottom: 40px`，紧随其后的 B 元素 `margin-top: 60px`，最终它们之间的间距是多少？如果你想让它变成 100px，有哪几种办法？

   <details><summary>参考答案</summary>

   间距是 60px（取大值，合并）。

   变成 100px 的办法：① 给其中一个包一层 BFC（`display: flow-root`）；② 把它们的父容器改成 flex/grid（子项 margin 不合并），间距改用 `gap` 或手动 margin 之和；③ 给中间插一个 border/padding 之类隔离物（但最不优雅）。

   现代推荐：直接用 flex/grid + `gap`，把"间距"交给专门的属性管。
   </details>

4. 一个 `z-index: 9999` 的弹窗，被一个 `z-index: 1` 的侧边栏盖住了。列出你应该排查的两个方向。

   <details><summary>参考答案</summary>

   方向一：弹窗自己是不是 `position: static`？static 元素 z-index 无效，先设 `position: relative/fixed`。

   方向二：弹窗和侧边栏是不是不在同一个层叠上下文？如果弹窗的父元素创建了层级更低的层叠上下文，弹窗再大也出不去——要把弹窗提升到更高层级的层叠上下文（或把弹窗 DOM 移到层级更高的祖先下），而不是无脑加 z-index。
   </details>

5. 解释 `sticky` 的吸附原理，并说出一条"sticky 失效"的常见原因及修法。

   <details><summary>参考答案</summary>

   原理：`sticky` 不脱离文档流，在滚动容器里滚到阈值（如 `top: 0`）前像 relative 待在原位，滚过阈值后像 fixed 一样吸在阈值处，但始终逃不出它的父容器范围。

   失效常见原因：① 没设阈值（`top` 缺省为 auto，永不吸）；② 父容器高度不够，没给元素留出可滚动的空间；③ 父容器或祖先有 `overflow: hidden`，把滚动容器"关"住了。

   修法：设 `top: 0`，确认父容器足够高、且滚动发生在正确的容器上。
   </details>

6. 一个卡片加了 `opacity: 0.9` 之后，里面的 `position: fixed` 弹窗突然盖不住页面其他元素了，为什么？怎么修？

   <details><summary>参考答案</summary>

   原因：`opacity < 1` 会让这个卡片创建一个新的层叠上下文，弹窗作为它的后代，被"锁死"在这个卡片的层级里。卡片的层级不够高，弹窗再大也浮不出去。

   修法：① 把弹窗的 DOM 移到卡片外面（提到 `<body>` 直接子级，层级最高的祖先下）；② 或者给卡片用 `isolation: isolate` 显式控制层级并理解其含义（治标）；③ 最稳妥是重构 DOM，让弹窗和"需要被它盖住的元素"处在同一层叠上下文里比较。
   </details>
