# 第 07 章 · 响应式布局最佳实践

> 前一章你学会了"选 Flex 还是 Grid"，但那只解决了"一个屏幕"里的问题。真实世界里，你的页面会在 320px 的手机、768px 的平板、1440px 的桌面、甚至 4K 显示器上被打开。
> 这一章教你**怎么让同一份 CSS 在不同屏幕上都成立**——从"移动优先"的写法顺序，到 `@media` 媒体查询、`@container` 容器查询，再到 `clamp()` 流式排版和响应式图片。
>
> 本章你需要记住的就一件事：**响应式不是"为大中小屏幕各写一套"，而是"写一套规则，让它自己适应宽度"。你越是想为每种屏幕写死样式，就越痛苦；越是学会"让规则随宽度流动"，就越轻松。**

---

## 7.1 移动优先：为什么从窄屏写起

这是本章最重要的一个观念，放在最前面讲。

### 先说结论：默认写窄屏，用 `min-width` 逐步放大

**移动优先（mobile-first）**的意思是：你的 CSS 里，**默认（不带任何媒体查询）的样式是给最窄的手机屏写的**，然后用 `@media (min-width: ...)` 一条一条地**往上加**，让它在更大的屏幕上也好看。

反过来，**桌面优先（desktop-first）**是：默认样式给大屏写，再用 `@media (max-width: ...)` 一条条**往下减**。

```css
/* ❌ 桌面优先：默认是桌面，往小屏"退化" */
.card { width: 300px; float: left; }            /* 默认三列并排 */
@media (max-width: 768px) {
  .card { width: 100%; float: none; }           /* 小屏改成单列 */
}

/* ✅ 移动优先：默认是手机，往大屏"增强" */
.card { width: 100%; }                          /* 默认单列堆叠 */
@media (min-width: 768px) {
  .card { width: 33.33%; float: left; }         /* 大屏才并排 */
}
```

两段代码**最终效果一样**：窄屏单列、宽屏三列。但写法顺序、心智负担、性能都不同。

### 为什么移动优先更好？三个硬理由

**理由一：窄屏布局更简单，先写简单的，符合"逐步增强"的认知规律。**

窄屏几乎永远是**单列堆叠**——内容从上往下排，没多少布局可做。宽屏才需要"分栏、并排、对齐"这些复杂操作。**从简单写到复杂，比从复杂倒退回简单，更容易想清楚。** 桌面优先意味着你一开始就要面对最复杂的布局，然后再思考"怎么把这些复杂的东西拆回小屏"。

**理由二：性能——移动设备（性能弱的机器）只匹配它需要的规则。**

这一点常被讲错，我在这里说准确：CSS 文件整体还是会被下载，**但"匹配"是有成本的**。

- 移动优先：默认规则就是移动端要的，**不需要媒体查询就生效**；大屏的增强规则用 `min-width` 包裹，**在窄屏上根本不匹配、不应用**。
- 桌面优先：默认规则是大屏的，移动端要先应用一遍大屏规则，**再用 `max-width` 的规则去覆盖、去撤销**（比如把 `float: left` 改回 `none`）。

一个 320px 的老手机，在桌面优先里要额外做一堆"先应用再撤销"的无用功；在移动优先里，它只应用自己真正需要的那些规则。**移动优先让"最弱的设备"干最少的活。**

**理由三：移动优先强制你聚焦核心内容。**

窄屏没地方放侧边栏、装饰、花哨的卡片，你必须想清楚"这个页面最重要的东西是什么"。**先设计移动版，等于先做了一次"内容优先级"的体检**。而那些"桌面优先"做出来的页面，往往塞满了一堆小屏根本放不下的东西，退化起来痛苦不堪。

### 逐步增强 vs 逐步退化

这两个词是对上面两种写法的概括，面试常考：

- **逐步增强（progressive enhancement）**：从一个**所有设备都支持的基础**出发（单列、纯 HTML 也能读），用 `min-width` 往上加能力。**坏处是"基础太朴素"，好处是"永远兜底"。**
- **逐步退化（graceful degradation）**：从一个**最完整的版本**出发（桌面全功能），用 `max-width` 往下删。**好处是"桌面最好看"，坏处是"小屏总有删不干净的东西"。**

移动优先对应**逐步增强**，桌面优先对应**逐步退化**。现代最佳实践**一边倒地选移动优先 + 逐步增强**，因为它更符合"最弱设备也能用"这个 web 的根本精神。

### 一个完整示例：从手机写到桌面

看一个"产品卡片列表"的移动优先完整写法，体会"往上加"的过程：

```html
<section class="products">
  <h2 class="products-title">热卖商品</h2>
  <div class="products-grid">
    <article class="card">...</article>
    <article class="card">...</article>
    <article class="card">...</article>
    <article class="card">...</article>
  </div>
</section>
```

```css
/* 第 0 层：默认 = 手机（320px~），单列堆叠，这是最基础、最重要的形态 */
.products-grid {
  display: grid;
  grid-template-columns: 1fr;      /* 单列 */
  gap: 16px;
  padding: 16px;
}
.products-title { font-size: 20px; }

/* 第 1 层：≥ 640px，卡片可以两列了 */
@media (min-width: 640px) {
  .products-grid { grid-template-columns: repeat(2, 1fr); }
  .products-title { font-size: 24px; }
}

/* 第 2 层：≥ 1024px，卡片三列，标题更大 */
@media (min-width: 1024px) {
  .products-grid { grid-template-columns: repeat(3, 1fr); gap: 24px; }
  .products-title { font-size: 32px; }
}
```

**读这段代码的顺序，就是"增强"的顺序**：先有单列（基础），再两列（增强），再三列（再增强）。每一层都只比上一层多一点点，心智负担小。反过来写（桌面优先），你得先写三列，再想"怎么把三列拆回两列、再拆回一列"。

> 一句话记住它：**移动优先 = 默认写窄屏、用 `min-width` 往上加；它更简单、性能更好、强制聚焦内容。桌面优先的 `max-width` 是"先应用再撤销"，让最弱的手机干最多的无用功。**

## 7.2 媒体查询 `@media` 完整用法

媒体查询是响应式的老骨干（1998 年就有雏形，2012 年响应式设计流行后成为标配）。这一节把它真正讲全。

### 7.2.1 `min-width` 和 `max-width`

这是最常用的两个。记一个永不混淆的心法：

- **`min-width`：屏幕"至少这么宽"才应用** → 用于"从小屏往上加"（移动优先）。
- **`max-width`：屏幕"最多这么宽"才应用** → 用于"从大屏往下减"（桌面优先）。

```css
/* min-width：宽度 ≥ 768px 时应用（往上加） */
@media (min-width: 768px) {
  .layout { display: grid; grid-template-columns: 220px 1fr; }
}

/* max-width：宽度 ≤ 480px 时应用（往下减） */
@media (max-width: 480px) {
  .card { padding: 12px; }  /* 小屏缩小内边距 */
}
```

**两个可以组合成"区间"**（在某个宽度范围内才生效）：

```css
/* 只在 768px ~ 1024px 之间生效（比如专门调平板） */
@media (min-width: 768px) and (max-width: 1024px) {
  .sidebar { display: none; }
}
```

**注意 `and` 是"与"的关系**：两个条件都要满足。如果你想表达"或"，得写两条独立的 `@media`。

### 7.2.2 `orientation`：横屏还是竖屏

```css
/* 横屏（宽 > 高） */
@media (orientation: landscape) {
  .gallery { grid-template-columns: repeat(4, 1fr); }
}

/* 竖屏（高 > 宽） */
@media (orientation: portrait) {
  .gallery { grid-template-columns: repeat(2, 1fr); }
}
```

**但说句实话**：`orientation` 现在**很少用**了。它判断的是"宽高谁大"，而真正影响布局的是**具体宽度**。一个横屏的折叠手机（宽 700px）和一个竖屏的小平板（宽 768px），布局需求其实差不多，`orientation` 却会把它们分到两类。

**更推荐的做法**：用 `min-width`/`max-width` 直接查宽度，或者用 `aspect-ratio` 查宽高比。`orientation` 只在极少数"横竖屏体验完全不同"的场景（比如游戏、视频播放器）才值得用。

### 7.2.3 `prefers-reduced-motion`：无障碍媒体查询

这是媒体查询里**最有温度**的一个：它不问屏幕，问的是**用户的操作系统设置**——用户是否在系统里开启了"减少动态效果"（很多前庭障碍、晕动症用户会开这个）。

```css
.hero {
  animation: slide-in 0.8s ease;
  transition: transform 0.3s;
}

/* 用户要求"少动"：关掉所有动画和过渡 */
@media (prefers-reduced-motion: reduce) {
  .hero {
    animation: none;
    transition: none;
  }
}
```

**为什么这个特别重要**：动画对有晕动症的用户来说不是"体验差"，是**生理不适**。你的花哨滚动动画，可能让一个用户头晕、恶心。给一条 `prefers-reduced-motion: reduce` 的兜底，是**无障碍（a11y）的基本修养**，也是面试里能加分的细节。

**它的两个取值**：`no-preference`（没设置，默认）和 `reduce`（要求减少）。写的时候只针对 `reduce` 处理即可。

**一个工程习惯**：很多人会把这个规则**放在所有 `@media` 的末尾**，作为"总兜底"，保证任何动画都能被这条关掉：

```css
/* 文件末尾：全局兜底，尊重用户的无障碍设置 */
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

### 7.2.4 断点选择策略：按"内容"设断点，不是按"设备"

这是响应式设计里最常被误解的一点。

**新手直觉**：按设备型号设断点——"iPhone 是 375px，Android 是 360px，iPad 是 768px……"

**这是错的。** 设备型号每年变，你今天给 iPhone 14 设的 390px，明年 iPhone 17 又是 393px。**追设备是追不完的。**

**正确做法**：**让内容自己"喊停"**——把你的布局在浏览器里从窄拖到宽，**盯着它看，哪一刻它"破了"（文字挤在一起、卡片太窄、空白太多），那一刻的宽度，就是一个断点。**

```css
/* 不是"iPhone 断点"，是"布局在这里破了"的断点 */
/* 320px 以下：手机竖屏，单列，没什么好写的（默认） */

@media (min-width: 600px) {
  /* 到这里，卡片可以两列了 */
  .cards { grid-template-columns: repeat(2, 1fr); }
}

@media (min-width: 900px) {
  /* 到这里，侧边栏可以放出来了 */
  .layout { grid-template-columns: 240px 1fr; }
}

@media (min-width: 1200px) {
  /* 到这里，卡片可以三列了 */
  .cards { grid-template-columns: repeat(3, 1fr); }
}
```

**断点命名应该描述"内容"，而不是"设备"**：`@media (min-width: 600px)` 比 `@media (max-width: 767px)` 好读，因为它告诉你"从这里开始两列"。如果非要用语义化的断点变量，也应该叫 `--bp-card-two-col` 而不是 `--bp-iphone`。

### 7.2.5 媒体查询的逻辑：`not` 和逗号（或）

前面只用到了 `and`（与），但媒体查询还有另外两个逻辑运算符：

**逗号 = "或"**：多个条件满足**任意一个**就应用：

```css
/* 手机竖屏 OR 手机横屏：只要宽度 ≤ 480px 就应用 */
@media (max-width: 480px), (orientation: portrait) and (max-width: 900px) {
  .nav { font-size: 14px; }
}
```

**`not` = "非"**：否定整个查询：

```css
/* 除了"宽度 ≥ 768px"之外的所有情况（即 < 768px） */
@media not (min-width: 768px) {
  .sidebar { display: none; }
}
```

**但说句实话**：`not` 和逗号**很少用**，因为移动优先下，`min-width` 的"往上加"模式本身就已经覆盖了绝大多数需求。你 90% 的时间只会写 `@media (min-width: 768px) { ... }` 这一种形式。了解 `and`/`not`/逗号是为了**读别人的代码**时不懵，而不是要你天天写。

### 7.2.6 其他高频媒体特性：`hover`、`pointer`、`prefers-color-scheme`

除了宽度，媒体查询还能问浏览器很多"能力"，下面三个最实用：

**`hover`：设备能不能悬停（有鼠标吗）**：

```css
/* 有鼠标的设备：悬停时显示下拉菜单 */
@media (hover: hover) {
  .dropdown:hover .menu { display: block; }
}

/* 触屏设备：没有悬停，改成点击展开（配合 JS） */
@media (hover: none) {
  .dropdown .menu { display: none; }
}
```

**`pointer`：主输入设备的精度**：

```css
/* 触摸屏（手指粗，命中区域要大） */
@media (pointer: coarse) {
  button { padding: 12px 20px; }   /* 触屏按钮做大点，方便手指点 */
}
```

`hover`/`pointer` 这两个**比 `orientation` 更值得用**——因为"有没有鼠标"比"横屏竖屏"更能决定交互方式。手机触屏没有 hover，你在触屏上写一堆 `:hover` 样式，用户永远触发不到。

**`prefers-color-scheme`：深色/浅色模式**：

```css
/* 用户在系统里开了深色模式 */
@media (prefers-color-scheme: dark) {
  :root {
    --bg: #1a1d23;
    --text: #e5e7eb;
  }
}
/* 浅色模式（或默认） */
:root {
  --bg: #fff;
  --text: #1a1d23;
}
body { background: var(--bg); color: var(--text); }
```

**注意**：深色模式的正确做法是**配合 CSS 变量**（上面这样），把颜色定义成变量、在媒体查询里换值。别在深色模式里一条条覆盖具体元素的颜色，那样会散落一地、改到吐血。

### 7.2.7 媒体查询该写在文件末尾，还是分散在各组件旁？

这是一个工程组织问题，两种风格都有，但**现代最佳实践偏向"分散"**。

**风格一：所有媒体查询集中写在文件末尾**（老式做法）：

```css
.card { ... }
.nav { ... }
.footer { ... }

/* 文件末尾，一堆 @media 堆在一起 */
@media (min-width: 768px) { .card { ... } }
@media (min-width: 768px) { .nav { ... } }
@media (min-width: 768px) { .footer { ... } }
```

**风格二：媒体查询紧跟在它要改的组件旁边**（推荐）：

```css
/* 每个组件的响应式规则，就写在组件自己的规则后面 */
.card { ... }
@media (min-width: 768px) { .card { ... } }

.nav { ... }
@media (min-width: 768px) { .nav { ... } }

.footer { ... }
@media (min-width: 768px) { .footer { ... } }
```

**为什么推荐风格二**：

1. **就近原则**：改一个组件时，它的响应式规则就在旁边，不用翻到文件末尾去找。
2. **删组件时一起删**：删掉 `.card` 相关的代码时，它的 `@media` 就在旁边，不会漏删文件末尾的孤魂。
3. **组件化友好**：现在的 CSS 都往"组件化"走（每个组件一个文件/一个块），媒体查询跟着组件走，是组件内聚的一部分。

**风格一的唯一优势**是"能一眼看到所有断点"，但代价是**维护时到处跳转**。除非你的 CSS 很短，否则选风格二。

> 一句话记住它：**`min-width` 往上加、`max-width` 往下减，`and` 组合区间、逗号是"或"；`prefers-reduced-motion` 尊重无障碍、`hover`/`pointer` 区分鼠标和触屏、`prefers-color-scheme` 做深色模式（配合 CSS 变量）；媒体查询就近写在组件旁边，别堆在文件末尾；断点按"内容破了"设，别按设备型号设。**

## 7.3 容器查询 `@container`

媒体查询查的是**视口（整个浏览器窗口）**的宽度；容器查询查的是**某个容器**的宽度。这一字之差，是响应式设计里近十年最大的一次进步。

### 为什么"查容器宽度"比"查视口宽度"更合理

先看一个真实的痛苦场景：**同一个组件，被放进不同宽度的父容器里。**

比如你写了一个"用户卡片"组件，它在主内容区（宽 800px）时应该横着排（头像在左、文字在右），在侧边栏（宽 260px）时应该竖着排（头像在上、文字在下）。

**用媒体查询（查视口）做，你会卡住**：媒体查询只知道"整个窗口多宽"，**它不知道这个组件自己待的坑有多宽**。于是你只能写一堆"组合条件"——"当窗口 ≥ 1200px **且** 这个卡片在侧边栏里"——可"在侧边栏里"这件事，媒体查询根本表达不了，你只能靠给不同位置的组件加不同 class，或者用 `:has()` 之类的新选择器硬凑。

```css
/* ❌ 媒体查询：只能查窗口，不知道卡片被塞进多宽的容器 */
@media (min-width: 1200px) {
  .card { flex-direction: row; }   /* 但侧边栏里的卡片也宽 260px，根本不该横排！ */
}
```

**用容器查询（查容器）做，问题直接消失**：

```html
<div class="card-container">   <!-- 这个容器可能宽 800px，也可能 260px -->
  <div class="card">
    <img class="card-avatar" src="avatar.jpg" alt="">
    <div class="card-text">...</div>
  </div>
</div>
```

```css
/* 把容器标记为"可查询" */
.card-container { container-type: inline-size; }

/* 问的是"容器"多宽，不是"窗口"多宽 */
@container (min-width: 400px) {
  .card { flex-direction: row; }   /* 容器够宽才横排 */
}
/* 容器 < 400px 时，保持默认的竖排 */
.card { display: flex; flex-direction: column; }
```

**这样，同一个 `.card` 组件，塞进 800px 的主内容区就自动横排，塞进 260px 的侧边栏就自动竖排**——你**只写一次**，它**自己适应所在的空间**。这就是"组件级的响应式"。

### 语法三件套

容器查询的核心语法就三步：

```css
/* ① 告诉浏览器：这个元素是"容器"，我要按它的宽度查询 */
.container {
  container-type: inline-size;   /* inline-size = 按"行内方向（宽度）"查询 */
  /* 或 container-type: size（宽高都查，但需显式给高度，用得少） */
}

/* ② 可选：给容器起个名字（多个容器时用于区分） */
.container {
  container-name: sidebar;
  container-type: inline-size;
}
/* 简写：container: sidebar / inline-size; */

/* ③ 在组件的子元素样式里，用 @container 查询 */
@container (min-width: 400px) {
  .child { ... }
}
/* 指定名字的查询 */
@container sidebar (min-width: 400px) {
  .child { ... }
}
```

### 浏览器支持情况

容器查询是较新的能力，支持时间线如下（**本教程写于 2026 年，已全面支持**）：

- Chrome / Edge **105**（2022 年 8 月）
- Safari **16**（2022 年 9 月）
- Firefox **110**（2023 年 2 月）

**到 2023 年，四大引擎全部落地**。现在（2026 年）你在生产里用容器查询，**基本不需要考虑兼容性垫片**——除非你的用户里有还在用 2021 年之前浏览器的极少数人。如果你必须兼容老浏览器，可以用 `@supports (container-type: inline-size)` 做特性检测，给老浏览器一个"退化的固定布局"。

### 一个真实的坑：`container-type` 会让容器宽度"塌掉"

这是容器查询**最容易踩的坑**，必须讲清楚。

`container-type: inline-size` 会给容器建立一个"尺寸包含（size containment）"——意思是**这个容器的宽度不再由它的内容撑开**，而是完全取决于外部给它分配的宽度。

```css
.card-container {
  container-type: inline-size;
  /* ❌ 忘了给它一个明确的宽度！ */
}
```

**现象**：如果这个容器是个普通的块级元素，块级元素默认宽度本该是"撑满父容器"，但 `container-type: inline-size` 建立 containment 后，如果没有明确的宽度来源，它的宽度可能塌成 0，里面的内容全消失了。

**正确做法**：给容器一个明确的宽度，或者让它处在"本来就有宽度"的位置：

```css
.card-container {
  container-type: inline-size;
  width: 100%;          /* ✅ 明确宽度来源 */
}
/* 或者：它本来就是 Grid 的一个格子，宽度由 grid 分配，就没问题 */
```

**记忆口诀**：`container-type` 之后，容器"不会自己长大"了，你得告诉它"你该多宽"。

### 容器查询长度单位：`cqw` 等

容器查询还带来了一组**新的长度单位**，它们相对的是**容器**而不是视口：

| 单位 | 含义 |
|---|---|
| `cqw` | 容器宽度的 1% |
| `cqh` | 容器高度的 1% |
| `cqi` | 容器行内方向（宽度）的 1% |
| `cqb` | 容器块方向（高度）的 1% |
| `cqmin` / `cqmax` | 容器宽高里较小 / 较大的那个的 1% |

**用途**：让组件内部的尺寸（字号、内边距、图片尺寸）**跟随容器缩放**，而不是跟随视口。这是"组件真正可复用"的关键——同一个组件放进大容器就变大、放进小容器就变小，而**不用改任何代码**：

```css
.card { container-type: inline-size; }

.card-title {
  /* 标题字号 = 容器宽度的 8%，但钳在 16~28px 之间 */
  font-size: clamp(16px, 8cqi, 28px);
}
.card-body {
  /* 内边距 = 容器宽度的 5% */
  padding: 5cqi;
}
```

**对比一下**：如果这里用 `vw`，字号跟随的是**整个窗口**，那侧边栏里的卡片（容器窄）标题也会被窗口宽度放大，比例就错了。用 `cqi`，它跟的是**容器自己的宽度**，永远成比例。**这就是"组件级响应式"的完整形态：`@container` 管结构突变，`cq` 单位管尺寸平滑跟随。**

### 媒体查询 vs 容器查询：一张对比表

| | `@media` 媒体查询 | `@container` 容器查询 |
|---|---|---|
| 查的是谁 | 视口（整个窗口） | 某个容器（父元素） |
| 粒度 | 页面级（整页一起变） | 组件级（单个组件自己变） |
| 典型场景 | 页面骨架换布局、隐藏侧边栏 | 组件被放进不同宽度的坑里 |
| 写法 | `@media (min-width: ...)` | 先 `container-type` 标记容器，再 `@container (min-width: ...)` |
| 支持 | 1998 年起，全兼容 | 2022~2023 年，已全面支持 |
| 关系 | 不是替代，是**分工** | 不是替代，是**分工** |

**结论**：媒体查询管"**这个页面在不同屏幕怎么摆**"，容器查询管"**这个组件在不同坑里怎么摆**"。**两者是分工关系，不是新旧替代。** 现实项目里，外层用媒体查询调骨架，内层用容器查询调组件，各司其职。

### 一个完整的实战：媒体查询搭骨架 + 容器查询调组件

把这一节串起来，看一个真实页面怎么做"两级响应式"：

```html
<div class="page">
  <aside class="page-side">侧边栏</aside>
  <main class="page-main">
    <!-- 这个列表会在主区（宽）里，也可能被挪到别的地方 -->
    <ul class="card-list">
      <li class="card">...</li>
      <li class="card">...</li>
      <li class="card">...</li>
    </ul>
  </main>
</div>
```

```css
/* ① 外层：媒体查询管"页面骨架"——窄屏单列，宽屏加侧边栏 */
.page { display: grid; grid-template-columns: 1fr; }
@media (min-width: 900px) {
  .page { grid-template-columns: 240px 1fr; }
}

/* ② 内层：容器查询管"组件适配"——列表放进多宽的坑，卡片就排几列 */
.card-list {
  container-type: inline-size;
  width: 100%;
  display: grid;
  grid-template-columns: 1fr;              /* 坑窄：单列 */
}
@container (min-width: 500px) {
  .card-list { grid-template-columns: repeat(2, 1fr); }  /* 坑中等：两列 */
}
@container (min-width: 800px) {
  .card-list { grid-template-columns: repeat(3, 1fr); }  /* 坑宽：三列 */
}
```

**这段代码的妙处**：`card-list` 的列数**由它自己所在容器的宽度决定**，而不是由窗口宽度决定。哪天产品经理说"把卡片列表也塞进侧边栏"，你**一个字都不用改**——列表进了窄的侧边栏，容器查询自动让它变回单列。

**这就是"组件级响应式"的价值**：组件变成了"自适应单元"，可以塞进任何地方，行为都是对的。媒体查询做不到这一点（它不知道组件被放哪了）。

> 一句话记住它：**媒体查询问"窗口多宽"，容器查询问"我待的坑多宽"——外层媒体查询搭骨架、内层容器查询调组件，组件才能变成"随便塞哪都适配"的自适应单元；记得 `container-type` 之后要给容器一个明确宽度，否则它会塌成 0。**

## 7.4 流式排版：`clamp()`、`min()`、`max()` 和视口单位

前面讲的都是"断点式"响应式——**在某个宽度，啪地切换**。但有些东西你不希望它"啪地切换"，而是希望它**随着宽度平滑地变**（比如字号、间距、图片尺寸）。这就用到"流式排版"。

### 7.4.1 视口单位：`vw` / `vh` / `dvh`

- `1vw` = 视口宽度的 1%。`100vw` = 整个视口宽度。
- `1vh` = 视口高度的 1%。`100vh` = 整个视口高度。
- `1vmin` = `vw` 和 `vh` 里**较小**的那个的 1%。
- `1vmax` = `vw` 和 `vh` 里**较大**的那个的 1%。

```css
.hero { height: 100vh; }      /* 占满一屏 */
.square { width: 50vmin; }    /* 取宽高里小的那个，保证不超出 */
```

**`vh` 在移动端的著名坑**：手机浏览器的地址栏是**会收缩/展开**的。地址栏展开时，可视区域变矮；`100vh` 取的是"地址栏收起来时的最大高度"，于是当地址栏展开，你的 `100vh` 元素底部会被地址栏**遮住**。

**解决**：用 `dvh`（动态视口高度，dynamic viewport height），它会**跟着地址栏的伸缩实时变化**：

```css
/* ❌ 移动端：100vh 在地址栏展开时，底部被遮住 */
.hero { height: 100vh; }

/* ✅ 用 dvh，跟随实际可视高度 */
.hero { height: 100dvh; }
```

`dvh` 的兄弟还有 `svh`（小视口，地址栏展开时的高度）和 `lvh`（大视口，地址栏收起时的高度）。**移动端"占满一屏"几乎总该用 `dvh`**。兼容性上，老浏览器不认 `dvh`，所以常见的兜底写法是**先写 `vh` 再写 `dvh`**：

```css
.hero { height: 100vh; }        /* 兜底：老浏览器 */
.hero { height: 100dvh; }       /* 新浏览器覆盖 */
```

### 7.4.2 `min()` 和 `max()`：取极值

`min()` 取所有参数里**最小**的值，`max()` 取**最大**的值。参数可以是**混合单位**（px 和 vw 混用）。

最经典的用法是"**宽度别超过一个上限**"：

```css
/* 内容区：宽度 = 100% 和 800px 里较小的那个 */
/* 也就是"最多 800px，小屏时占满" */
.content { width: min(100%, 800px); }
```

这比老写法优雅太多。老写法要先 `width: 100%; max-width: 800px;` 两行，还得处理"小屏时不想留边距"的细节。`min()` 一行搞定。

`max()` 反过来，用于"别小于一个下限"：

```css
/* 按钮：至少 120px，大屏时 30% 宽 */
.btn { width: max(120px, 30%); }
```

### 7.4.3 `clamp()`：流体字号的最佳实践

`clamp(MIN, 理想值, MAX)` 的语义是：**取"理想值"，但把它钳在 MIN 和 MAX 之间**。

它是**流式字体**的标配：

```css
h1 {
  /* 字号 = 2.5vw，但最小 24px、最大 48px */
  font-size: clamp(24px, 2.5vw, 48px);
}
```

**效果**：屏幕很窄时，`2.5vw` 会小到离谱，但被 `24px` 这个下限挡住；屏幕很宽时，`2.5vw` 会大到爆炸，但被 `48px` 这个上限挡住；中间区间，字号**随宽度平滑变化**，不再需要一堆 `@media` 断点去改字号。

**为什么这是最佳实践**：以前做"响应式字号"要写一堆断点：

```css
/* ❌ 老办法：一堆断点，每档之间还有跳变 */
h1 { font-size: 24px; }
@media (min-width: 640px) { h1 { font-size: 32px; } }
@media (min-width: 1024px) { h1 { font-size: 40px; } }
@media (min-width: 1440px) { h1 { font-size: 48px; } }
```

`clamp()` 一行替换掉这一坨，还**没有跳变**（在 640px 那一点不会"啪"地变大）。

**一个细节**：`clamp()` 里的"理想值"用 `vw` 时，记得考虑"它到底对应多大的屏"。`2.5vw` 在 320px 屏上是 8px（太小，被下限挡住），在 1920px 屏上是 48px（正好到上限）。**你可以反推**：想让字号在 320px 时是下限、1920px 时是上限，`vw` 系数 = (上限 - 下限) / (大屏宽 - 小屏宽)，再换算成百分比。不想算也没关系，先写个大概值，拖窗口看效果微调。

### 7.4.4 三者组合：间距也用流式

流式排版不只给字号用，**间距、圆角、图片尺寸**都可以：

```css
.card {
  /* 内边距随宽度平滑变化，但不会太小也不会太大 */
  padding: clamp(12px, 3vw, 32px);
  /* 圆角也流式 */
  border-radius: clamp(4px, 1vw, 12px);
  /* 卡片宽度：最多 400px，小屏占满 */
  width: min(100%, 400px);
}
```

### 7.4.5 `calc()`：让"流式"更精确

`calc()` 是 CSS 的"计算器"，能在**不同单位之间做加减乘除**（乘除有 `*` `/`，但 `*` 和 `/` 至少一边是数字）。它常和 `clamp()`、`min()` 配合，让流式排版更精确。

最常见的用法是**"一个固定部分 + 一个流式部分"**：

```css
/* 内容区宽度：占满，但两侧各留 24px */
.content { width: calc(100% - 48px); }

/* 侧边栏宽度：20% 但至少留出 120px 的间隙 */
.main { width: calc(100% - 240px); }
```

**和 `clamp()` 组合，做"精确的流体字号"**（7.4.3 提到过"反推系数"，用 `calc` 能写得更直白）：

```css
/* 让字号在 320px 屏是 28px、1440px 屏是 56px，中间线性变化 */
h1 {
  font-size: clamp(
    28px,
    calc(28px + (56 - 28) * ((100vw - 320px) / (1440 - 320))),
    56px
  );
}
```

这段看着吓人，但拆开就懂了：`(100vw - 320px) / (1440 - 320)` 是一个**0 到 1 的进度**（320px 时是 0，1440px 时是 1），乘以 `(56 - 28)` 得到"从 0 到 28px 的增量"，加上基准 `28px`，就是"从 28px 平滑长到 56px"。**这种"进度条"式的写法，是精确控制流体字号的通用公式。**

**`calc()` 里的 `vw` 部分，本质是"把视口宽度映射成 0~1 进度"，再映射成你想要的值区间。** 掌握这个映射思路，任何"随宽度线性变化"的尺寸你都能写。

> 一句话记住它：**`clamp(MIN, 理想, MAX)` 是流式排版的核心——让字号/间距随宽度平滑变、又被上下限兜住；`calc()` 做跨单位计算，`calc(28px + 28 * ((100vw - 320px) / 1120))` 这种"进度条"公式能精确控制流体值；移动端占满一屏用 `dvh` 别用 `vh`。**

## 7.4.6 流式排版 vs 断点式：什么时候用哪个

学了 `clamp()` 之后，你可能想把所有响应式都改成流式。**别。** 两者各有分工：

- **流式（`clamp`/`min`/`max`）**：适合**连续的量**——字号、间距、圆角、图片尺寸。这些量"每多 1px 就该变一点点"，用断点会跳变、且要写一堆。
- **断点式（`@media`/`@container`）**：适合**结构性的变**——单列变两列、侧边栏显隐、横排变竖排。这些是"非此即彼"的突变，用流式做不到。

```css
/* 流式：字号连续变，用 clamp */
h1 { font-size: clamp(24px, 2.5vw, 48px); }

/* 断点式：结构突变，用 @media */
@media (min-width: 768px) {
  .layout { grid-template-columns: 220px 1fr; }  /* 单列变两列 */
}
```

**判断口诀**：**"变多宽"用流式，"变几列"用断点。** 现实里两者是混合的——外层断点切结构，内层 `clamp` 调字号。下一章你会看到 Tailwind 里也有对应的 `clamp()` 工具类，同一套思想。

> 一句话记住它：**"变多宽/多大"用流式（`clamp`），"变几列/显隐"用断点（`@media`/`@container`）；两者混合使用，别偏废。**

## 7.5 响应式图片与 `aspect-ratio`、`object-fit`

布局响应式了，图片不响应式，等于白做——**图片通常是页面上最重的资源**，也是"布局抖动（CLS）"的最大来源。这一节讲三件事：图片怎么按屏幕加载不同尺寸、怎么保持比例、怎么裁剪。

### 7.5.1 `srcset` + `sizes`：按屏幕加载不同尺寸的图

核心思想：**别让手机去下载一张给 4K 屏看的 4000px 大图**。用 `srcset` 给浏览器提供多个尺寸的候选，让浏览器**自己挑最合适的下载**。

```html
<img
  srcset="cat-small.jpg 480w,
          cat-medium.jpg 800w,
          cat-large.jpg 1200w"
  sizes="(max-width: 600px) 480px,
         800px"
  src="cat-large.jpg"
  alt="一只猫">
```

**这段在说什么**：

- `srcset`：我提供了三张图，宽度分别是 480w、800w、1200w（`w` = 实际像素宽度）。
- `sizes`：告诉浏览器"这张图在页面上实际显示多宽"——屏幕 ≤ 600px 时显示 480px，否则显示 800px。
- `src`：兜底，浏览器不支持 `srcset` 时用这个。

浏览器拿着 `sizes`（图上显示多大）和屏幕的 DPR（设备像素比，Retina 屏是 2），算出"该下载多大像素的图"，再去 `srcset` 里挑**最接近且不低于需求**的那张。

**一句话理解**：`srcset` 是"菜单"，`sizes` 是"我实际吃多大的量"，浏览器据此下单。

### 7.5.2 `<picture>` + `<source>`：按条件切换不同图

`srcset` 解决"同一张图的不同尺寸"，`<picture>` 解决"**不同条件用不同的图**"（比如手机看竖版图、桌面看横版图，或不同格式）。

```html
<picture>
  <!-- 大屏：用横版大图 -->
  <source media="(min-width: 800px)" srcset="hero-wide.jpg">
  <!-- 中屏：用横版小图 -->
  <source media="(min-width: 480px)" srcset="hero-medium.jpg">
  <!-- 默认（小屏）：用竖版图 -->
  <img src="hero-tall.jpg" alt="横幅">
</picture>
```

**规则**：浏览器从上往下读 `<source>`，**第一个 `media` 条件匹配的**就采用它的 `srcset`，全不匹配就用 `<img>` 的 `src`。

**什么时候用谁**：

- 同一张图、只要不同尺寸 → `srcset` + `sizes`。
- 不同构图（横/竖）、不同格式（webp/avif 兜底）→ `<picture>`。

**`<picture>` 最常见的实际用途：格式兜底。** WebP 和 AVIF 格式体积比 JPEG/PNG 小 30%~50%，但老浏览器不一定支持。用 `<picture>` 让新浏览器吃小体积的新格式，老浏览器退回 JPEG：

```html
<picture>
  <!-- 支持 AVIF 的浏览器用最省流的 AVIF -->
  <source type="image/avif" srcset="photo.avif">
  <!-- 支持 WebP 的用 WebP -->
  <source type="image/webp" srcset="photo.webp">
  <!-- 都不支持，退回 JPEG -->
  <img src="photo.jpg" alt="照片">
</picture>
```

浏览器会按 `<source>` 顺序，**采用第一个它认识的 `type`**。这一手几乎零成本，就能让图片省 1/3 的流量。

### 7.5.3 `aspect-ratio`：给图片占位，防"布局抖动"

图片没加载出来之前，浏览器不知道它多高，于是**页面布局会先按 0 高度排，图一加载出来，内容"啪"地往下跳**。这就是 Core Web Vitals 里的 **CLS（Cumulative Layout Shift，累积布局偏移）**，是性能评分里重要的一项。

**解决**：用 `aspect-ratio` 提前告诉浏览器"这张图的宽高比是多少"，浏览器就能**先占好位置**，图加载出来后直接填进去，不会跳：

```css
.card img {
  aspect-ratio: 16 / 9;   /* 告诉浏览器：宽高比 16:9 */
  width: 100%;
}
```

**效果**：图片还没加载时，`.card img` 就占着"宽度 100%、按 16:9 算出的高度"这个坑，文字和按钮都排好了位置。图来了，直接填充，**布局纹丝不动**。

### 7.5.4 `object-fit`：怎么把图塞进这个比例

设了 `aspect-ratio: 16/9` 后，如果图片本身不是 16:9（比如一张 1:1 的方图），它会被**拉伸变形**（默认 `object-fit: fill`）。`object-fit` 就是解决"图和坑比例不符"的：

```css
.card img {
  width: 100%;
  aspect-ratio: 16 / 9;
  object-fit: cover;   /* 填满坑，多余部分裁掉，不变形 */
}
```

- `cover`：**填满**坑，保持比例，**多余的部分裁掉**（最常用，头像/卡片图都用它）。
- `contain`：**完整显示**整张图，保持比例，**可能留白**（用于"必须看到全图"的场景）。
- `fill`：填满坑但**拉伸变形**（默认，几乎别用）。

**配合 `object-position`** 还能控制"裁掉哪部分"（比如人脸在上方，就 `object-position: top`）：

```css
.avatar {
  width: 48px;
  height: 48px;
  object-fit: cover;
  object-position: top;   /* 裁图时优先保留顶部（脸通常在顶部） */
}
```

### 7.5.5 懒加载：`loading="lazy"`（一行省一半流量）

图片是最重的资源，而**用户根本不看页面下方还没滚到的图**。所以"滚动到了再加载"（懒加载）是性能优化的大头。

好消息是，现代浏览器把这个能力**原生内置**了，只要在 `<img>` 上加一个属性：

```html
<!-- 只有滚动到接近这张图时，浏览器才开始下载 -->
<img src="far-below.jpg" alt="页面下方的图" loading="lazy">
```

**用法就这一行**，没有 JS、没有库。配合响应式图片（`srcset`）一起用：

```html
<img src="hero.jpg" loading="lazy" srcset="..." sizes="..." alt="...">
```

**一个细节**：**首屏的图不要加 `loading="lazy"`**。首屏图本该立刻加载，加了 `lazy` 反而会延迟它的出现（浏览器要等布局确定后才判断"它是不是在首屏"）。经验法则是：**首屏用默认（立即加载），首屏之外的图都加 `lazy`**。

`loading` 有两个值：`eager`（默认，立即加载）和 `lazy`（懒加载）。还有一个配套属性 `decoding="async"`，让图片解码不阻塞渲染，也可以顺手加上。

> 一句话记住它：**`srcset` 按屏幕下载合适尺寸，`<picture>` 按条件/格式切换（WebP/AVIF 省 1/3 流量）；`aspect-ratio` 提前占位防 CLS，`object-fit: cover` 填满裁剪不变形；首屏之外的图加 `loading="lazy"` 一行省一半流量。**

## 7.6 常见断点方案：Tailwind 的 sm/md/lg/xl/2xl 与自定义断点

前面 7.2.4 说了"按内容设断点"，但现实里很多人直接抄一套**现成的断点方案**，其中最有名的是 **Tailwind CSS 的默认断点**。这一节讲这套方案的值、以及它和"自定义断点"怎么取舍。

### Tailwind 的默认断点

Tailwind（第 08、09 章会细讲）预设了五个断点，**全部是 `min-width`（移动优先）**：

| 断点名 | 值 | 含义（屏幕至少这么宽） |
|---|---|---|
| `sm` | 640px | 大手机横屏 / 小平板 |
| `md` | 768px | 平板 |
| `lg` | 1024px | 笔记本 |
| `xl` | 1280px | 桌面 |
| `2xl` | 1536px | 大桌面 |

在 Tailwind 里，你写 `md:grid-cols-2`，它编译出来就是 `@media (min-width: 768px) { ... }`——**前缀 `md:` 对应"从 768px 开始"**。

**这套断点的价值**：

1. **约定俗成，团队不用吵**。"这个组件在平板上该变样"——直接用 `md:`，谁都不用重新发明断点。
2. **移动优先内置**：全是 `min-width`，逼着你从窄屏写起。
3. **覆盖了绝大多数场景**：五个档位，从手机到 4K 都够用。

**这套断点的代价**：

1. **它是"猜的"**。640/768/1024 这些数字，历史上大致对应"某几款设备"，但**它不知道你的具体内容在哪破了**。你的侧边栏可能 700px 就该收起来，但 Tailwind 断点里 700px 正好卡在 `sm`（640）和 `md`（768）之间，你得选一个、或将就。
2. **不是所有项目都适配**。一个"桌面端管理后台"（用户几乎全在 1280px+ 的屏幕），那 `sm`/`md` 这些档位基本用不上；一个"纯手机 H5 页"，`xl`/`2xl` 又是摆设。

### 自定义断点的取舍

**结论先行**：**小项目/快速原型，直接抄 Tailwind 断点（或同类方案）最省心；大项目/对视觉有要求的项目，值得自己按内容定断点。**

如果你要自定义，两条原则：

**原则一：断点用 `min-width`，命名描述内容，不描述设备。**

```css
/* ✅ 好：断点描述"从什么时候开始变两列" */
@media (min-width: 600px) { ... }

/* ❌ 差：描述设备，且用 max-width（桌面优先思维） */
@media (max-width: 767px) { ... }
```

**原则二：断点要少而精，通常 3~4 个就够。**

太多断点意味着你在维护一堆"只有某一小段宽度才生效"的规则，几乎不可能记全、测全。**3~4 个断点（手机、平板、桌面、大桌面）覆盖 95% 的场景。** 如果某个组件真的需要额外断点，用容器查询（7.3）在组件内部解决，而不是给全局再加一个断点。

### 用 CSS 变量统一管理断点

不管用哪套方案，把断点值抽成 CSS 变量，改起来只动一处：

```css
:root {
  --bp-sm: 640px;
  --bp-md: 768px;
  --bp-lg: 1024px;
}
/* 注意：媒体查询里不能直接用 var()（老浏览器不支持），
   所以这套变量更多是"文档作用"，真正的断点还是要手写数值，
   或者配合 CSS 预处理器的 $ 变量 / Tailwind 的配置 */
@media (min-width: 768px) { ... }  /* 对应 var(--bp-md) */
```

**这里有个真实的坑**：**CSS 变量在 `@media` 的条件里不能用**（`@media (min-width: var(--bp-md))` 是无效的，媒体查询条件里不允许 `var()`）。所以如果你想"改一处断点全局生效"，得靠**预处理器变量**（Sass 的 `$bp-md`）或 **Tailwind 配置**，而不是原生 CSS 变量。原生 CSS 里，断点值只能"手写 + 注释对齐"。

### 三种典型项目的断点策略

没有"放之四海而皆准"的断点，因为**不同项目的主流设备完全不同**。看三个典型场景：

**场景一：纯手机 H5 页（活动页、营销页）**

用户几乎全在手机（320px~430px），桌面版是"顺手兼容"。这时断点只需要**一个**——"手机"和"其他"的分界，通常设在 640px 左右：

```css
/* 默认：手机，单列 */
/* ≥ 640px：平板/桌面，最多两列，居中限宽 */
@media (min-width: 640px) {
  .container { max-width: 640px; margin: 0 auto; }
}
```

这种项目**用 Tailwind 的 `sm/md/lg/xl/2xl` 就浪费了**——`xl`、`2xl` 那些档位用户根本不会触发。

**场景二：响应式官网/博客（本教程默认场景）**

用户从手机到 4K 都有，这是**最需要完整断点**的场景。Tailwind 的五个断点（640/768/1024/1280/1536）基本够用，或按内容自定 3~4 个。

**场景三：桌面端管理后台**

用户几乎全在 1280px+ 的屏幕（后台不会用手机开）。这时**响应式是次要的**，重点是在 1440px 上布局好看。断点可以只设一个"窄窗口兜底"（窗口被用户拖窄了别崩）：

```css
/* 默认：桌面，侧边栏展开 */
/* < 1024px：窗口被拖窄了，收起侧边栏 */
@media (max-width: 1024px) {
  .sidebar { display: none; }
}
```

注意这里**甚至用了 `max-width`**（桌面优先）——因为这种项目的"基础形态"本来就是桌面，从桌面往下兜底反而更自然。**移动优先是"默认规则"，但当你的用户压根不在移动端时，桌面优先也不是罪。** 关键是**想清楚你的主流用户在哪个宽度**。

> 一句话记住它：**Tailwind 的 sm/md/lg/xl/2xl（640/768/1024/1280/1536）是一套"移动优先、约定俗成"的断点，官网/博客直接抄最省心；但 H5 页和桌面后台的断点策略完全不同——断点要匹配"你的主流用户在哪"，不是无脑套一套。注意 `@media` 条件里不能用 CSS 变量。**

## 7.7 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 桌面优先用 `max-width` 写响应式 | 小屏上样式要"先应用再撤销"，且容易漏撤销 | 默认就是桌面样式，移动端要逐条覆盖 | 移动优先：默认窄屏，`min-width` 往上加 |
| 移动端 `100vh` 底边被地址栏遮住 | 全屏元素底部看不见了 | 移动浏览器地址栏伸缩，`vh` 取的是收起时的高度 | 用 `100dvh`（老浏览器兜底 `100vh`） |
| 按设备型号设断点 | 断点一堆，还追不上新手机 | 设备型号每年变，断点追不完 | 按"内容破了"的宽度设断点，少而精 |
| 媒体查询里写 `var()` | 断点不生效 | `@media` 条件里不允许 `var()` | 断点值手写，或用预处理器/Tailwind 变量 |
| `container-type` 后容器宽度塌成 0 | 容器内容消失 | `container-type` 建立尺寸包含，容器不再由内容撑宽 | 给容器明确宽度（`width: 100%` 或让它当 Grid 格子） |
| 想用容器查询查"自己" | `@container` 不生效 | 容器查询查的是**祖先**容器，不能查自身 | 在组件**外层**包一个 `container-type` 的父容器 |
| 图片加载导致布局跳动 | 页面加载时内容"啪"地往下跳 | 图片未加载时高度未知，占位为 0 | 给图片 `aspect-ratio` 提前占位（防 CLS） |
| `object-fit` 默认拉伸变形 | 图片被拉宽或压扁 | 默认 `object-fit: fill` 会破坏比例 | 用 `object-fit: cover`（填满裁剪）或 `contain`（完整留白） |
| 忘记 `prefers-reduced-motion` | 晕动症用户被动画"晃晕" | 动画对部分用户是生理不适 | 加 `@media (prefers-reduced-motion: reduce)` 关动画兜底 |
| `orientation` 用来分横竖屏布局 | 横屏折叠机和竖屏平板被错分 | `orientation` 只比宽高，不看具体宽度 | 用 `min-width`/`max-width` 或 `aspect-ratio` 查宽高比 |

---

## 7.8 本章小结

- **移动优先**：默认写窄屏、`min-width` 往上加；更简单、性能更好、强制聚焦内容；对应"逐步增强"。
- **媒体查询**：`min-width`（往上加）、`max-width`（往下减）、`and` 组合区间；`prefers-reduced-motion: reduce` 是无障碍兜底；断点按内容设。
- **容器查询**：查"容器宽度"而非"窗口宽度"，实现组件级响应式；2023 年全浏览器支持；`container-type` 后要给容器明确宽度。
- **流式排版**：`clamp(MIN, 理想, MAX)` 让字号/间距平滑变；移动端用 `dvh`；`min(100%, 800px)` 一行替代 `width + max-width`。
- **响应式图片**：`srcset` 按屏幕下载、`<picture>` 按条件切换、`aspect-ratio` 防 CLS、`object-fit: cover` 裁剪不变形。
- **断点方案**：Tailwind 五档（640/768/1024/1280/1536）可抄；自定义断点少而精、按内容设；`@media` 里不能用 CSS 变量。
- **一句话**：响应式是"写一套随宽度流动的规则"，不是"为每种屏幕各写一套"。

## 7.9 动手练习

1. **改错**：下面这段 CSS 是桌面优先写法，请改成移动优先写法（等价效果即可）。

```css
   .layout { display: flex; }
   .sidebar { width: 240px; }
   .content { flex: 1; }
   @media (max-width: 768px) {
     .layout { flex-direction: column; }
     .sidebar { width: 100%; }
   }
```

   <details><summary>参考答案</summary>

```css
   .layout { display: flex; flex-direction: column; }   /* 默认单列 */
   .sidebar { width: 100%; }
   .content { flex: 1; }
   @media (min-width: 768px) {
     .layout { flex-direction: row; }
     .sidebar { width: 240px; }
   }
```

   默认（窄屏）单列堆叠，≥768px 才横过来、侧边栏才定宽。
   </details>

2. **选型**：一个"用户卡片"组件，会被同时用在宽 800px 的主区和宽 260px 的侧边栏里。主区里要横排（头像左、文字右），侧边栏里要竖排。请说明为什么用媒体查询做不对，并给出容器查询的写法。

   <details><summary>参考答案</summary>

   媒体查询只能查视口宽度，无法知道卡片自己待的容器是 800px 还是 260px，所以同一个卡片无法在两种容器里呈现不同布局。

```css
   .card-wrapper { container-type: inline-size; width: 100%; }
   .card { display: flex; flex-direction: column; }        /* 默认竖排 */
   @container (min-width: 400px) {
     .card { flex-direction: row; }                          /* 容器够宽才横排 */
   }
```
   </details>

3. **写一段流体字号**：让 `h1` 的字号在 320px 屏上不小于 28px，在 1440px 屏上不大于 56px，中间随宽度平滑变化。用 `clamp()` 一行写出。

   <details><summary>参考答案</summary>

```css
   h1 { font-size: clamp(28px, 2.5vw + 20px, 56px); }
```

   简单版 `clamp(28px, 4vw, 56px)` 也可用（320px 时 4vw≈12.8px 被 28 兜住，1440px 时 4vw≈57.6px 被 56 兜住）。`2.5vw + 20px` 这种"vw + 固定值"的写法能更精确地对齐两个端点，是更精细的做法。
   </details>

4. **判断**：下面的说法对不对？"`<picture>` 和 `srcset` 作用一样，都是给不同屏幕加载不同尺寸的图片。"

   <details><summary>参考答案</summary>

   不完全对。`srcset`（配合 `sizes`）解决"**同一张图**的不同尺寸"——浏览器按屏幕和 DPR 挑最合适的分辨率。`<picture>`（配合 `<source media>`）解决"**不同条件用不同图**"——按媒体条件切换完全不同的图片（横版/竖版、不同格式）。两者可以组合，但用途不同。
   </details>

5. **实战**：一个全屏横幅（`hero`）要求：占满一屏高度（移动端地址栏展开也不能被遮）、背景是一张 16:9 的图（裁剪填充、不变形）、并且用户在系统里开启"减少动态效果"时，横幅上的文字动画要关闭。请写出这三部分的 CSS。

   <details><summary>参考答案</summary>

```css
   .hero {
     height: 100vh;        /* 兜底：老浏览器 */
     height: 100dvh;       /* 移动端地址栏伸缩也不被遮 */
   }
   .hero-bg {
     width: 100%;
     height: 100%;
     object-fit: cover;    /* 填满 + 裁剪 + 不变形 */
   }
   @media (prefers-reduced-motion: reduce) {
     .hero-title { animation: none; transition: none; }
   }
```
   </details>

6. **改错**：下面这段 CSS 想做"深色模式"，请指出问题并修正。

```css
   /* ❌ 想做深色模式 */
   @media (prefers-color-scheme: dark) {
     .header { background: #111; }
     .footer { background: #111; }
     .text { color: #eee; }
     .link { color: #9cf; }
   }
```

   <details><summary>参考答案</summary>

   问题：颜色值散落在每个元素的选择器里，组件一多就失控，改主题要翻遍所有规则。正确做法是把颜色抽成 CSS 变量，在媒体查询里只换变量的值：

```css
   :root {
     --bg: #fff; --text: #1a1d23; --link: #06c;
   }
   @media (prefers-color-scheme: dark) {
     :root { --bg: #111; --text: #eee; --link: #9cf; }
   }
   body { background: var(--bg); color: var(--text); }
   a { color: var(--link); }
```
   </details>

7. **实战**：一个"评论区"组件要被放进宽 900px 的主区和宽 300px 的侧边栏里。要求：主区里每条评论是"头像在左、内容在右"的横排，侧边栏里是"头像在上、内容在下"的竖排，且头像尺寸跟随容器宽度（`cqw`）平滑缩放。请写出完整 CSS。

   <details><summary>参考答案</summary>

```css
   .comment-list { container-type: inline-size; width: 100%; }

   .comment { display: flex; flex-direction: column; gap: 8px; }  /* 默认竖排 */
   @container (min-width: 400px) {
     .comment { flex-direction: row; }                              /* 容器够宽才横排 */
   }
   .comment-avatar {
     width: clamp(32px, 12cqi, 56px);    /* 头像跟随容器宽度缩放 */
     aspect-ratio: 1;
     object-fit: cover;
   }
```

   关键点：容器查询管"结构突变"（横排/竖排），`cqw` 单位管"尺寸平滑跟随"（头像大小），两者配合，组件放进任何宽度的容器都自动适配。
   </details>
